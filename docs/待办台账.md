# 待办台账

> **给人看的清单，一眼答「现在干什么、为什么还没干」。** 一行一条，列填不满的去详情。
> 详情（卡在哪、要动哪些文件、踩过的坑）→ `docs/待办台账-详情.md`；**那份是给下一棒 AI 看的，人不用翻**。做完的 → `docs/archive/已完成_YYYYMM.md`。
> **编号是历史留下的身份证，不是顺序**。**本表 `#n` 只属于本库**：剧库有自己的 `#n`（它家待办）、报上来的是 `GQ-n`，同号不同事，别混着看。
> 2026-11-08 改形态：原「一档 / 二档 / 三档」用的是三把尺子（许可 / 目标 / 阻塞性），同一条能同时落进三档，于是「只开这一条线」永远兑现不了。改成「等什么」一列。
> **2026-11-09 定分节法：只用一个维度——「卡在谁身上」**。任何库任何待办，阻塞只在这四方之一，所以这一套搬到别的库照样成立。**别按内容分类**（工具 / 文档 / 业务）——那是每个库自己的事，换库就失效；也别按进度分类（没开工 / 在做 / 待验）——同一条会在几档之间来回跳。
> **2026-11-10 降维：等协作方 / 等外部并成「等回音」，「等谁」降为列**（等谁 / 从哪天）。维度不变——还是「卡在谁身上」，降的是节数：等谁本来是条目属性不是结构维度，将来冒出新等待方加一行数据就行，不开新节。依据电脑管家建议件（`E:/Workedbuddy/电脑管家/10_在办/待办分类降维建议_20261110.md`，赵哥 11-10 拍板采纳）。
> **一条同时等两样的，归到先动的那一方。** 节名答粗问题（卡在谁），「等谁」「等什么」列答细问题（等哪位 / 等哪件事）。

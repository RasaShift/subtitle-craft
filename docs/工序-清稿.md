# 工序 · 清稿

> **这是哪一步**：「通用工序定义」的第二份，管「拿到一份字幕，先把不用判断的错清掉」。
> **管什么**：规则能说清「改成什么」的改动——命中即改，不逐条判。
> **不绑什么**：不出现剧名、季号、集号规则。换一份字幕，只要有规则清单就能跑。

## 1. 这道工序解决什么

清稿专治「**不用看语境就知道错**」的：贴字、残留标签、译名错写、符号被吃、空白与换行。

它和另两道工序的分界不是「错得轻」，而是**改动需不需要判断**：

| 例子 | 判 |
|---|---|
| 「你好.」句号是半角、紧贴汉字 | 改法唯一 → 清稿 |
| 这个逗号该不该加、这句该不该断 | 两种都通 → 退回对稿 / 审稿 |

**不做会怎样**：脏输入让后两道工序大面积假红（旧库实测 #114a、#124 的必看表里一半是假信号），而这类错留在成品里读者一眼看得见。

## 2. 输入

| 输入 | 必需 | 干什么 |
|---|---|---|
| 字幕文件（SRT / ASS） | 是 | 改的对象；一次只动一份 |
| 规则清单 | 是 | 决定「什么算 100% 确定」；没有清单就不是清稿，是随手改 |
| 词表（专名 / 术语） | **否** | 三列：原文 / 规定译法 / 已见错写法。有它才查得了「译名统一」；替换纪律见规则清单 `MT1` |
| 样式基准（模板文件或参数表） | **否** | 文件层专用：编码、画布坐标、样式表、字体字号、描边底纹「统一成什么」都从这里取，见规则清单 |
| 参照轨 | **否** | 清稿不看别人写了什么——这是它和对稿最大的区别 |

**词表第三列填之前先问三句**（2026-11-08 加，两次实测）：① 它是不是**任一条规定译法的一部分**？是 → 替换后叠字（`伯纳`→`伯纳德` 得「伯纳德德」，一集 9 处），`text_scan` 现在直接拒绝加载；② 它是不是**剧情里故意保留的错叫**？是 → 改掉笑点就没了，归对稿/审稿判，不进机改；③ **同一人名的简称/全名剧级一次定死**，写进接活单，不许逐集决定——否则要么词表塞进几百处简称，要么事后全库回改。

## 3. 判断路径（一问定生死）

```
一条命中
  ├─ 规则能不能说清「改成什么」，且换个人来改结果一样？
  │     ├─ 能 ────────────────→ 直接改（stage=mech，不逐条判）
  │     └─ 不能 ──────────────→ 不进本工序，退回对稿 / 审稿
  └─ 规则本身不确定（同一处两种改法都通）→ 退回对稿 / 审稿
```

**一句话判据：改法唯一 = 机械，归本工序；改法有二 = 判断，退回对稿 / 审稿。**
「机械」在这里说的是**性质**（不用判断），不是工序名——工序叫清稿。这条判据同时解释了为什么本工序覆盖面比名字暗示的小：多数「格式问题」其实是判断问题。

## 4. 两层：改「每条的字」，还是改「整份文件的样式」

同一个工序，两类活，粒度和落地工具都不一样：

| 层 | 改什么 | 谁落 |
|---|---|---|
| 文本层 | 每条字幕的中文字符串：译名错写、标签残留、贴字 | `tools/land_verify.py`（条号 + 旧文本锚点） |
| **文件层** | 整份文件的结构与样式：编码 / BOM、画布坐标、样式表、字体字号、描边底纹、样式引用 | `tools/style_normalize.py`（基准 + 画布比例；`0×0` 与旧样式名必须显式声明，不许猜） |

两层各自能走多远、有哪些规则、哪些「看着像机械其实不是」，逐条列在 `docs/工序-清稿-规则清单.md`（按规则加行，别往这里堆）。

**关键一点**：文件层的「统一成什么」不是天生的唯一解，必须先有**样式基准**（模板或参数表）。这和文本层要靠词表是同一个道理——**没有基准就没有唯一改法，也就不算清稿**，只是把四种面孔换成第五种。

文件层最容易被低估的是三条防呆（画布比例必须对得上视频、样式名一改引用静默回落、换字体后字宽变），细见规则清单第四节。

## 5. 顺序（硬约束）

```
文件层（结构 / 样式）→ 文本层（逐条字符）→ 对稿 → 审稿
```

理由是双向的：

- **文件层要在文本层之前**：它重写整行但不动文本，跑完文本锚点仍有效；反过来先改文本，样式器还得把文本原样保住再对一遍账；
- **整体要在对稿之前**：脏输入（粘连带歪英文切词、贴字让两轨词流错位）会让后两道报一堆假信号；
- **不能往后放**：对稿跑完再回头机械改，同一条字幕会被两段各声明一次——见第 6 节，那正是静默丢改动的地方。

## 6. 落地：两段改动不能各改同一条（2026-11-05 实测）

**现象**：改动清单里同一条出现两行（清稿清单去空格 + 对稿候选改数字）→ `apply` 报「应改 2 实改 2」，`verify` 报「声明 1 / 在位 1 / 多改 0」、退出码 0，而文件里只剩后一条。

**原因**：`apply` 每条都按**原文件**文本算替换，后一行覆盖前一行；`verify` 用「条号 → 声明」去重，两条并成一条，于是复算全绿。

**修法**：`read_changes` 遇到重复条号直接退出码 2，不再静默。同一条有多处要改，先在清单里合成一行（一条字幕只能有一个最终文本）。

**正确串行**：清稿清单先落盘 → 拿落盘后的文件重跑对稿 → 对稿的旧文本以新文件为准。
拿改前文本生成的对稿清单，在清稿清单落地后会逐条「锚点失配」被跳过——**看到大量跳过就停下来重跑对稿，不许当成没事**（跳过不报错是这条链路的安全设计，也是最容易被忽略的地方）。

> 旧库记过同类坑：`标准工序规范_20261025.md` §3.1 三坑之一「批量 findings 撞已有行号被 merge 静默丢」。同一个失效模式换了工具名又出现一次——所以这次写成断言，不写成提醒。

## 7. 输出

改动清单落 TSV，前三列是落地器认的，后两列是事后查账用的：

| 字段 | 内容 |
|---|---|
| `no` | 字幕条号，不改不动 |
| `old` | 逐字照抄；抄错会让落地环节找不到位置（锚点失配） |
| `new` | 改后的中文段；折行不归本工序管 |
| `rule` | 哪条规则干的，写规则号（`MT1` / `MF2`）——**不许写「规则名」那种含糊话** |
| `evidence` | 命中的原文片段，必须能当场复算 |
| `source` / `stage` | `source` = 谁执行的（脚本名或 `human`）；`stage=mech` |

统计固定报一行：`清稿清单 N 条（规则 a×n / b×n）`。

## 8. 三问与完成标志

| 三问 | 答案 |
|---|---|
| **触发条件** | 每集开工、对稿与审稿之前先跑；另可按需单开（如只清一句的贴字）。**统筹方负责触发** |
| **完成标志** | ① 改动清单逐条读完（不判红，但必须看）② `apply` 实改数 = 声明数、跳过 0 ③ 同一批规则重扫命中归零（不幂等的规则要写明为什么） |
| **不跑会怎样** | 脏输入让后两道假红；成品留着读者看得见的脏。代价不是硬伤，是「能看但不够干净」+ 下游误判 |

**别把清稿算进另两道工序的完成度**。三者各自计数，报「某集完成」必须带是哪一道——混着算会让进度虚高（旧库 S03 就栽在这里：1149 条里 987 条是格式线）。

## 10. 禁区

1. **改法有二就不是清稿**。为了「一次全清」把判断类规则塞进来，等于把判据偷偷放宽。
2. **不许手工改成品**。写操作只有一条合法路径：改动清单 → `apply` → `verify`。
3. **同一行不许两段各声明**（工具已拦重复条号；人工也不许绕）。
4. **跑完要重扫归零**，不是「跑过就行」——没有归零就说明规则与改动对不上。

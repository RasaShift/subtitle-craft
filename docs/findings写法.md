# 字幕 findings 编写（docs/findings写法.md）

> **举证与实测数据**：**本文各条自带**——集号（S01E02 / 01x01）、条数（525 条返工、37 条里 12 条）、事故原因都写在条目里，没有单独的实证文件。
> **改规矩前先读这些标记**；它们是规矩的依据，不是规矩本身。含真实集号，只留本地。

把一批判读结果写成 `findings/<集>.json`。**只管「怎么写」**——该不该改的判据不在这里（查表判据见 `subtitle-clean`，对轨判据见 `subtitle-align`）。

通用纪律（触发声明、冲突优先级、证据纪律、简报格式、禁区）**只在一处定义**：`docs/判断纪律.md` 技能——动手前先加载它，本文件不抄。

## 干什么

| | 路径 |
|---|---|
| 输入 | 判读结果（判定表 / 裁决草稿 / 批次结论） |
| 输出 | `02_工作区/<季>/findings/<季号>x<集号>.json`（**只追加** `findings` / `inserts` 数组） |

## 字段纪律（写错会被静默丢弃或被拒）

| 字段 | 规矩 | 后果 |
|---|---|---|
| `season` | 两位字符串 `"01"`，**不是数字** | 写错静默丢弃 |
| `episode` | `"01x01"` 字符串 | 同上 |
| `ln` | 源字幕行号 | 行号不存在 → 四重定位拒 |
| `cn` | **与源字幕逐字一致**（含空格） | 不一致 → apply 拒（`accept.py` 第 5 项报红） |
| `cn_new` | 改后的中文 | — |
| `evidence` | 必填；纪律见《总则》第 3 节 | 空/编造 → 第 6/7 项报红 |
| `source_model` | 规则名 / 模型名 / `human` | 缺了三个月后查不出谁干的 |
| `layer` | `form` / `align` / `sentence` | 缺了分不清哪层产出 |

> **⚠️ 这两个字段名跟本库《命名准则》不一致，但文件里不能改。**
> 准则 2026-11-06 判过：`source_model` 一个字段装了两种东西，应拆成 `rule`（规则名）+ `source`（模型名 / `human`）；`layer` 与「层」撞义，应改成 `stage`（`mech` / `triage` / `read`）。
> **改文档没用**：`finding_lint.py` 第 38 行 `META = ('type','layer','source_model')`、`dialogue_proof.py` 四处读 `source_model`，认的都是旧名。只改文档，脚本会把整批判成「字段缺失」报黄。
> **改名的前提是先改脚本**，且老 findings 要能兼容读。这条已记进台账，别单独改文档。
| `tc` | 时间码——**抄源字幕的 `start`**（用 `iter_rows` 打出来抄），**不是抄官方 SRT**；官方时间只用来定位上下文 | 抄成官方时间码 → merge「时间码不符」**整条静默丢弃**。2026-10-27 S01E02 实测：同一句官方 19:48.354 / 我们 19:48.88 |

> 5.1 三字段（`source_model`/`layer`/`evidence`）是 续一 525 条返工教训换来的硬要求。

## 特殊改动的写法

1. **补行** → 进 `inserts` 数组，不占 `findings` 的 `ln` 序列；成品行数差会与 inserts 数对账（`accept.py` 第 3 项）。
2. **两行中文整体错位（句群）** → 老库走 `02_工作区/<季>/groups/<集>.json` 声明整组（哪几行、各改成什么），整组同进退（`verify` V21 查「组内全改或全不改」）。**本库的 `land_verify.py` 没有这个功能**，只有单行双锚点；整段重排挂在 `README.md`「已知不足」里。**遇到句群就交回统筹方，别用单行替换硬改**——硬改会把位置搞乱。
3. **只改英文轨（中文没错）** → `cn_new` **仍然必填**，填**与原中文完全相同**（merge 只认 `cn_new` 非空；
   留空会被判「缺少改法」直接丢弃，2026-10-27 S01E02 L411 实测丢过一条），`en_after` 写目标英文。
   `cn_new == cn` 且 `en_after` 存在时 merge 不当 no-op，正常保留。
4. **分片/行号一律来自源字幕**，不是成品——`cn` 要跟源字幕对，不是跟成品对。
5. **对轨层（`layer: align`）的条目** —— `type` / `severity` 按下面这张表选，**别一律写 `missing`**
   （2026-10-28 #99 定：S01E03–E12 那批 7 条全是英文轨修词，却照旧一律写 `missing`/`must`，
   等于把拼写修混进了「补漏」的账，以后按 type 统计「补了多少缺失」会失真）：

   | `type` | 什么时候用 | `severity` |
   |---|---|---|
   | `en_typo` | 英文轨的拼写错、语法不成立、词形/大小写错、两词粘连——**同一个词或同一句里的形** | `should` |
   | `missing` | 英文听错、漏掉内容（官方有、我们这句没说到）——**行还在，内容没了** | `must` |
   | `错译` | 纯中文错译、中英互相矛盾，**英文轨本身是对的** | `must` |
   | `错位` | 分段/行序结构问题，靠 `groups` 整组落，不写单行 | `must` |

   **这张表只对新条目生效**：已经落地的 findings 一个字不改——回头重写历史账要重审全部旧判定，
   收益抵不上代价。
   **它不属于判据类改动**：`type` 不参与「改/不改」的判定，也不在 `drop_reason` 的静默丢弃条件里
   （那四条是 season／cn_new 空／tc 抄官方／ln-cn 不符），只决定归类统计，所以不用跑回归。

   要动英文时给 `en_after`。
   中文跟不跟着改，看**中文的错是不是由英文轨错引起**：是 → 一并写 `cn_new`；中文本来就译对 → 只给 `en_after`，不动中文（如 01x01 L659 中文已把被截断的后半句译出）。
   **只写「可内部判定」的条目**：技术性缺陷（截断/拼写/语法）或内部矛盾（英中不一致、与术语表冲突）。
   两边都通顺的**内容分歧属「听写分歧」——不改、不进 findings**，写进判定表并在简报汇总（判据见 `judge-shared` 禁区第 9 条）。
   `layer` / `source_model` / `en_after` 这三样在对轨层是必填，别照抄查表层的写法。

6. **官方有整句、我们中英都没有** → 判**不改**、**不补行**，归「我们缺」工序抽看，**不写进 findings**
   （2026-10-28 #100 定；实例：01x09 L118|119 官方有 `Lunch is at two.`，我们英文和中文都没有这一句。**该英文句是脱敏时换上去的自造句，不是剧目原文**）。

   理由：这类是「整句缺失」，定义上就该进「我们缺」清单；补行走 `inserts`，一动就要对账成品行数差，
   为一句钟点单开补行不值，且「我们缺」清单实测噪声极大（E02 那批 27 条里 26 条是假缺）。

   > **别把它写成 `missing`**：`missing` 说的是「我们这行还在、但内容听错或漏了」（如把一句听成半句）；
   > 「整句没有」是另一回事，写了会让 `inserts` 对账和「我们缺」统计两头都错。

## 硬约束（除《总则》禁区外，本工序特有）

- **只追加**：不许改已有条目、不许删、不许重建文件。
- 判「不改」的也要留记录（判定表层面），别只写「改」的。
- 写完不跑 `merge`/`apply`/`verify`——那是统筹方的活。

## 写完自查（交回前跑，全过再交）

```bash
cd <工具目录>                              # 由派活单给；没写就问，别自己找
python finding_lint.py --season S0x        # 第一步，必须跑到 0
python accept.py --season S0x --expect-findings <N> --expect-inserts <M>
```

**`finding_lint` 是必跑的第一步。** 它把你写错的条直接标出来，每条带一句怎么改：

- 红：行号不存在 / 时间码不符 / 中文原文不符 / `cn_new` 空 / no-op / 同集重复行号（这几类 merge 会**静默丢弃**，命令行只报个数）
- 红：evidence 引文在「官方 SRT + 源字幕英文」里都查不到（验收第 7 项会红）
- 黄：`type`/`layer`/`source_model` 缺失、换行符风格不一致、confidence 越界（不影响落地，但查不出这条改动的来源）

退出码非 0 就是还有红项，**改到 0 再交回**。它调的是 `dialogue_proof.drop_reason`，与 merge 同一份判定——「lint 过了 merge 还丢」这种事不会再有。

然后跑 `accept`，重点看第 5/6/7 项（cn 逐字、evidence 空、evidence 查无出处）——这三项就是本工序的质量闸。第 1/2/3 项对不上预期条数，先核对自己的写入再喊冤。

> 这一节只加自检动作，不改判定口径，所以不触发回归；改判据类条款才要跑。

## 交回什么

《总则》第 4 节三件：findings 数据 + 简报（大白话在前）+ 自检结果。简报数表里写清「处理条数 / 判改 / 判不改 / 新增 findings / 补行」。

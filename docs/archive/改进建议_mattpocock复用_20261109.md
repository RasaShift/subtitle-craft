## 三、逐条

### 1（P0）· `做法.md:46` 的「缺」改指针

**现状（原文）**：

> | skill 编写规范 + 验收清单 | 有 | 无 | **缺**。判据在上游决策第五、六节：**未验证的判据不进技能**；同一件事做第二次、且做法与第一次不同才升技能；判据进 `docs/工序-*.md`，技能只留薄壳。技能 9→4 已于 11-07 拆完，这份规范仍没落——要做时单开一条，别再挂在这里 |

**病因**：它说判据在"上游决策第五、六节"，而 `README.md:29` 写着"上游决策文档**不随本仓库发布**"。两句合起来 = **这条判据在本库一个字都没有**。这与本库第一条硬规矩「一份内容只有一个真身」直接冲突：这里不是"多了一份副本"，是**没有真身**。

**改法**（第三列「缺」整格替换，不改行结构）：

```
**缺**。判据改用 `writing-for-agents` 技能（全局技能，`~/.workbuddy/skills/writing-for-agents/`，
中文版 1.1 起稳定）；写技能前加载它读判据。**本库只保留一条 override**：判据进
`docs/工序-*.md`，技能只留目录 + 指路表，不放命令、不放脚本名、不放判据条文。
上游决策第五、六节不再作为引用来源（那份不随库发布）。
```

**为什么不是新增一份规范文档**：`writing-for-agents` 第 78–79 行自己写着"让每个 meaning 保持在 single source of truth""把 one-file、one-command 的 lookups 留给 environment"。把它的五条判据抄进本库，正好违反它自己的两条判据，而且抄本会立刻开始漂。

**怎么验**：改完 `grep -n "上游决策第五" docs/`，应零命中（`README.md:29` 那处是解释"为什么不发布"，可保留）。

**顺带一条**：`做法.md:46` 里"技能 9→4 已于 11-07 拆完"是历史，按本库「讲现在是什么状态」的写法，这句可以一并删。

### 2（P0）· `判断纪律.md:15` 同一个病

**现状（原文）**：

> 本批流程细节见当批派活单；脚本怎么跑见本库 `tools/` 下各脚本的 `--help`（原指向上游《标准工序规范》，那份不在本库）。

**病因**：括号里这句话的作用是"说明这个指针为什么指不到"，但它留在正文里，读者每次都要读一遍"这里曾经有个东西、它不在"。这是**负资产**：一个指不到的指针，比没有指针更费注意力。

**改法**：整句替换为

> 本批流程细节见当批派活单；脚本怎么跑见本库 `tools/` 下各脚本的 `--help`。

**怎么验**：`grep -n "标准工序规范" docs/` 应零命中。

### 3（P1）· 新增 `GLOSSARY.md`

**为什么该建**：本库与剧库不共享代码，靠"词"通信。剧库读本库判据，判据里写「档位」「`T?`」「补行」「错位区间」，剧库得知道这些词指什么——**现在没有任何一处能查**。

**已经出过事**：`协作协议.md` §5 的 `GQ-3`「**「集目录」一词二义**」，处理方式是人肉发现、改文档关掉。同类风险还有 `做法.md` 第四节那条「再出现『同一事实两个数、两个说法』算复发」。

**格式**（直接用，不要自创）：`GLOSSARY-FORMAT.md` 四条规则——

1. **敢下判断**：多个词指同一概念时选最好的那个，其余列 `_Avoid_` 下
2. **定义最多两句**：定义它是什么，不是它做什么
3. **只收本项目独有的词**：通用编程概念（timeout、error type）不进
4. 同义词列 `_Avoid_` 下

**初版收这 10 个**（按第 3 条筛过，全部是本库自造）：

| 词 | 定义（初稿，维护方改） | `_Avoid_` |
|---|---|---|
| 真身 | 一份内容唯一权威的位置，别处只许引 `文件:行号` | 权威来源、唯一定义处 |
| 档位 | 审稿读多深，只有两个值：全量 / 关键点 | 档期、深度 |
| 薄壳 | 技能里只放"什么时候用、去哪查"，不放判据条文 | 壳、索引页 |
| 卡点 | 干活方撞墙的事实，四列，不写改法 | 问题、bug |
| `GQ` | 干活方提给维护方的改进建议编号，编号只在待报通用库维护；`#n` 是攒批报的另一套编号，两套并存不归并 | — |
| 补行 | 往成品里插一条新字幕行，位置按时间算 | 插行、加行 |
| 错位区间 | 两条轨整体错开的那几段，由人划、工具只消费 | 偏移段 |
| `T?` | 对稿四类结论里"拿不准"的那类，必须人过，一条不留 | 待定、存疑 |
| 三级阶梯 | 坑的三种防法：判定记录一行 → 脚本断言 → 钩子拦截 | — |
| 判红四分 | 验收报红的四种归属：成品错 / 清单错 / 工具错 / 底线错 | — |

**配套改动**（两处，各一行）：

- `docs/文档落点表.md` 加一行：`| 词是什么意思（本库自造词） | GLOSSARY.md（库根） | 100 |`
- `tools/doc_lint.py` 的 `LIMITS` 加：`'GLOSSARY.md': {'lines': 100, 'entry': 0}`

**明确不写进 GLOSSARY 的**：`词表.tsv`（那是剧目业务数据）、怎么判（那是工序文档）、任何剧名集号。

**怎么验**：`python tools/doc_lint.py` 不报 ERROR；拿 `GQ-3` 那条旧事故回查——「集目录」这个词现在能在 GLOSSARY 里查到唯一含义，或明确列为 `_Avoid_`。

### 4（P1）· 落点表补两行（其中一行是本库真缺口）

**4b. 缺一类：外部建议放哪。**

### 5（P2）· 派活单模板补齐三道工序

**现状**：`做法.md:45` 自己写着「**部分覆盖**：审稿那条链有模板；其余工序仍是对话里现写，不可复现」。

**借什么**：mattpocock 的 **context pointer** 原则——`handoff` 第 12 行："不要重复已经被其他 artifacts 捕获的内容……改用 path 或 URL 引用它们"。

**为什么优先级只给 P2**：`做法.md:45` 把这条归在「等活来了再立」，本文同意，**只是把"该怎么立"写清**，免得下次又从头想。

## 五、明确不建议改的（附理由）

用户提的原则是「能覆盖或替换就不改造」，但**覆盖的前提是对方更好**。这五项本库已经更强或已覆盖：

| 不建议 | 本库现状 | 理由 |
|---|---|---|
| 判定记录改 ADR 格式 | 一条三行、带重开条件、卷制、当前卷 ≤150 行、判过不做的也记 | ADR 只有"三道门"和"可以只有一段"。本库多出"重开条件"和卷制，改过去是降级 |
| 交接文档改 `handoff` | ≤100 行 + 四段 + 「收工≠交接」+ 收官即归档 | `handoff` 只到"压成一份 md"，本库多了时机判断和归档纪律 |
| 三级硬隔离阶梯改 `retro` | 判定记录一行 → 脚本断言 → 钩子拦截，判据「这个错犯了，有没有东西会自动喊？」 | `retro` 出的是**建议**，本库是**强制**。改过去等于把硬约束降成软建议 |
| 接棒必读改 `ask-matt` | 一页目录 + 17 行"去哪查"表 | `ask-matt` 是"问它该用哪个技能"，本库是"东西在哪"，两件事。且 `做法.md:42` 已批过加第三层导航 |
| 装 engineering 那 19 个技能 | — | 全部依赖 issue tracker、branch、PR。本库没有这些，装了是空转 |

另外：`wayfinder` 原版依赖 issue tracker 的 native blocking 和 assignee 认领，在剧库那种目录体系里跑不动。剧库若已在用本地 `WAYFINDER.md` 形态，**继续用本地的**，不要换原版。

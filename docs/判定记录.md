## 2026-11-08

### 定档排在切分之前：先定工作量，再摊派

- **结论**：审稿开工顺序定为 **圈回顾段 → 定档 → 切两片（仅全量档）**。关键点档不切。
- **理由**：定档三条判据（来源先验 / 抽 40 条 / 对稿候选数）一条都不依赖分片；分片只为全量档准备，而分片有成本（实测 2 人切片比不切片贵 1.44 积分、慢 71 秒）。**先切等于按最贵的方案备料，再发现用不上。** `工序-审稿.md` 原写「先定档」是对的，错的是手册把定档漏在开工准备之外。
- **重开条件**：出现「不切片就没法定档」的判据（例如必须整片通读才能判来源）。

### 接活八问单独成文：「问」这个动作原先是空白

- **结论**：新建 `docs/接活单.md`，八问 + 每问的答案落点，**只问不判**；入口挂在 `examples/新剧接入.md` 第 0 步（同一行内加指针，不增行，仍 210/210）。
- **理由**：四道工序全在答「给定一份字幕怎么处理」，没有「这份字幕是什么、要什么」。定档第一条判据「来源先验」原文靠看片头猜，实际得问人。八问的答案本来就散在 `定档.md` / 派活单 / 新剧接入三处，但**采集动作**整条链上没有一处——写成独立文件是因为 `文档落点表` 明写「再长说明加了新步骤，那时重估，不是在这里硬塞」。
- **重开条件**：八问里有两问连续三次没人答得上来，说明问法不对，改问法不改结构。

### 切片是负收益（单集实测，n=1）

- **结论**：全量档 **优先按遍派、不切片**；「每片 2 个 Agent」这个形状本身没被数据支持。
- **理由**：四配法对照（同一集 913 条正片，真值取四组并集 69 条、扣 2 条假阳、分母 67）：1 人合一遍 25% / **2 人分两遍不切片 61%** / 2 人切片各合一遍 52% / 4 人切片分两遍 79%。B 与 C 是纯对照（同 2 人、同覆盖两遍，只差切不切），**C 三项全输**：召回 −9 点、慢 71 秒、贵 1.44 积分。
- **重开条件**：换一集复跑 B vs C，结论翻转说明与集结构有关（跨片呼应多的集切片更伤），那时按集型分档，**不恢复「一律切片」**。

### 派活成本按积分算，「子 Agent 占 2%」作废

- **结论**：成本口径统一为「每个召回点花多少积分」：1 人 0.67 / **2 人分两遍 0.20（最省）** / 2 人切片 0.27 / 4 人分片 0.23。
- **理由**：「子 Agent 占 2%」是循环论证（`skills/agent-craft` 早已判死：加 Agent 是双向涨），却被手册当成「推荐 4 个」的唯一成本依据——方法论判死了，工序文档没回流。实测反证：**1 人被 2 人两头压制**（召回 2.4 倍、钱只要 74%）；4 人单价只比 2 人高 15%。**真正的坑是 1 人和切片，不是 4 人。**
- **重开条件**：积分是用户目测（累计 16.84→29.23→43.06→61.45），拿到精确用量且结论翻转时以精确值重算。

### 判据指了路必须同时设闸，否则路径可绕开

- **结论**：`工序-审稿.md` 第 6 节把「十四条全不命中 → 不改，命中任一 → 应改」改成「**没读过十四条，这句话是空的，不许开判**」，并把「不带七种形态差一个数量级」从手册搬进来；完成标志加第 ⑤ 条——`tools/check_rules.py` 通过才算完（`rule` 全在判据表 33 条内、**C1 组不为零**，为零直接拒）。
- **理由**：原写法是「指路 + 一句听起来完整的空结论」，读者会以为已经拿到判据。全库四处指路，没有一处能拦人（对比切片的「不过先停下报」——那有退出码）。实证：第一遍读 548 条只报 11 条，C1 一条没有，密度 2.0 贴着下限。
- **重开条件**：`check_rules` 只验编号不验判断，出现「编号全对但判错方向」的批次，说明闸只能防没读、防不了读歪，那时要另加盲测。

### 验收挖出三个落地工具错，都在 in-place 主路径上

- **结论**：`land_verify.py` 修三处——① in-place 写完盘拿已被覆盖的 `src` 当「改前」，必报满「旧文本在改前就找不到」；② `load()` 按**后缀**判类型，`.bak` 被当 SRT 解析出 0 条，等于「拿备份重验」这条路是死的；③ 提示语把**行数**当条数填（`len(bb)` → `len(bc)`，输出过「991 + 0 = 0」这种自相矛盾）。自检 224 → **229**。
- **理由**：in-place 是常规用法，不修则每一集验收都稳定误判打回，而文件其实改对了。**224 条自检全绿却没抓到**，因为用例全是手动 `apply` + 单独写 `dst` + `verify`，从没走过 `main()` 的 in-place 分支——主路径没人测。新用例已按本库规矩「先造错看它认不认」验过（撤掉修复 → 2 条 FAIL、退出码 1）。
- **重开条件**：无（纯缺陷）。

### 密度下限没有定义，分批落地会稳定误报

- **结论**：判据 1.8–7.0 只写了「超出**上限**要解释」，**没写低于下限怎么办**；分批落地（只落某一层）时按**本批声明**算密度，不按全量算。
- **理由**：本次只落 C1 15 条，密度 1.54 触发 ⚠；若按全量并集 67 条算约 6.9，落在区间内。同一形状一天出现两次（片1 读到 2.0 贴下限、验收 1.54 破下限），每次都要临时找解释。
- **重开条件**：工序文档补上「分批落地」概念并写清密度口径之后，此条作废。

### 三方口径不一致时补工具，不删检查

- **结论**：新建 `tools/mk_meta.py` 产 `meta.json`。**不**把 `mk_worksheet` 改复杂（它只管一个行号区间，不知道全片多少条），也**不**把 `meta.json` 降为可选。
- **理由**：手册说它是必需产物、`mk_worksheet` 只出 tsv、`check_slices` 又把它当可选——三方各说各的，结果是每集手写一份，字段名只能翻源码猜（`skipped` 写成数字 `0` 直接 `AttributeError`）。降为可选等于把 `check_slices` 的前两项对账拆掉，那是闸。**顺带一个教训**：`meta.rows` 必须是**各片行数相加**（不含 skipped），第一版写成了源总条数，`check_slices` 当场报「各片相加=913，meta.rows=973」——手册 `:126` 明写着这条口径，是没回核。
- **重开条件**：换一部剧跑一次；若那边的分片表不叫 `片N.tsv`，加一个命名参数，不改接口骨架。

### 不分公开库与私用库：脏活放剧库，本库只收结论

- **结论**：**不新建"私用工作台库"**。分层照旧——脏活（实验、试跑、半成品、真实数据）全放剧库 `03_工作区/`，本库只收提炼后的结论。准入尺写进 `docs/文档落点表.md` 的引言行（表头上方那段 `>`）：**换个人、换部剧还成立吗？** 成立才进。
- **理由**：① 本库天生不是工作台（没有片源、没有 `02_工作区`），干活时被**引用**不被**写入**——11-08 一整天 9 个子 Agent、6700 条次阅读、三个新产物全落在剧库 `exp/`，本库一个字没沾，分层是现成的；② 分两个库会造出**第二份真身**，工具改一处要同步两处，正是当天批判两次的病；③ 物理隔离只防「忘了删」，防不了「本来就不该写」，真防线是准入判断。
- **配套两条**：实证文件只写「为什么定这条」（换个人读有用），不写「我怎么犯的错」（日记）；能被机器执行的进库，要人养习惯的不进库——判据 `手册:75`「规矩写在卡里 ≠ 流程里有一步」。
- **重开条件**：出现「本库必须收一份不能公开的数据才能工作」的情况（例如工具要读剧库真名表），那时再拆，拆的依据是那份数据，不是习惯。

### 交接说明归剧库所有，本库不再维护副本

- **结论**：`是大臣系列/通用库交接说明_20261108.md` 是**剧库的文件**。本库不代改、不复制、不在台账里跟踪它；本库只负责自己的 `README` / `docs/工序-*.md` / `examples/新剧接入.md` 是对的。
- **理由**：它在剧库，本库的 `doc_lint`、git、台账三样都管不到，必然腐烂——**11-08 当天写完，当天就被实测推翻三处**（UTF-16 说有/无 BOM 写反、全量档估时差 3–4 倍、密度单位写成条/百条）。同一件事的第二份真身，烂了没人知道。
- **重开条件**：本库需要对外提供一份「接手说明」模板时——那时它进本库 `examples/`、由本库维护，剧库不再各存一份。

### 库外交接文字只写动作，不写结论

- **结论**：写给剧库的东西**不抄判据、不抄数值**——编码形态、估时、密度区间、单位一律不转述，只写「去哪份文档的哪一节看」和「跑哪条命令自己查」。
- **理由**：11-08 那份交接说明四处错（UTF-16 有无 BOM、全量档 40–60 分钟、密度写成条/百条、`.bak` 要不要另备），**没有一处是原创判断，全是转述来的数字和术语**——违反本库第 1 条常驻原则「一份内容只有一个真身，别处只留指针」。且它在库外，`doc_lint` 与 git 都管不到，**错了三天没人发现**。反过来写动作就不会错：「别先转码，直接跑 `subtitle_probe.py`，读出来是空再处理」——错了当场看得见。
- **重开条件**：库外文字能被体检时（例如这类交接件放回本库 `examples/` 下、进 `doc_lint` 范围）——那时可以写结论，但仍要带出处。

### 台账用「等什么」一列，不设档

- **结论**：`docs/待办台账.md` 弃「一档 / 二档 / 三档」，改成一张表 + 「等什么」一列（值只有 `随时可做` / `等 <具体那件事>` / `等你拍板`），顶上单独标「现在手上」一条。
- **理由**：原三档用了**三把尺子**——一档是许可（准不准开工）、二档是目标（离完成差多少）、三档是阻塞性（挡不挡发布），同一条能同时落进三档，所以「只开这一条线」永远兑现不了（改之前一档有 4 条）。二档那句「通往推 GitHub 的缺口」随 `#7` 完成也已过期。抄自 `日常杂活` 的台账形态：它不分档，但每条必须填「等什么」，**填不出说明这条还没想清楚**——把分类判断换成一条可填的事实。
- **重开条件**：出现「等什么」填不出来、但必须记的事（例如悬着的方向性问题），那时单开一节，**不恢复分档**。

### `#13` 工序合订本判不做（11-08 复核）

- **理由**：① 仓库 11-07 已公开，`docs/` 就在仓库里，合订本没有额外读者；② 它必然是**第二份真身**——8 份 770 行生成出来，改了源件忘了重出就是错的，还得写 `doc_bundle.py --check` 防漂移，成本是持续的；③ 11-06 判的「真痛点是不知道看哪份、不是看不全」仍成立，导航已由 README / 接棒必读 / 落点表管住。

### 画布纵向取交付高度，不取片源分辨率

- **结论**：`MF2` 从「PlayRes 等于片源的实际分辨率」改成「**宽高比 = 显示宽高比，纵向 = 交付高度 1080**」：16:9 → 1920×1080、4:3 → 1440×1080、2.35:1 → 2538×1080，片源低于 1080 就 upscale 交付。`style_normalize base` 加一道 WARN：纵向缩放超出 0.75–1.5 就喊。
- **理由**：三套预设母版都是 1080 高，而剧库片源是 720×576。照旧判据写成 `720x576` 或按 DAR 补的 `768x576`，`base` 实测字号 79→42、描边 2→1，预设当场失效；更糟的是**工具不拒**——它把 720×576 当显示分辨率（1.25）算横向，两处都错且无声。纵向对齐母版后，1440×1080 下 79/2 原样搬过来，只换横轴（实测）。**11-06 那条不是被推翻**：它怕「文件写 72、画面是 48」，交付 1080 时渲染 1:1，那个顾虑不存在——它错在把渲染基准当成了片源分辨率。
- **重开条件**：出现「必须按原分辨率交付、不许 upscale」的剧——纵向取片源高度、预设按比例缩成该剧专用的一份。判据不变，只是交付高度变成参数。

### 配对表带来源，旧表只提示

- **结论**：`bilingual_pairs` 产的第 11 列 `来源`（`文件名@时刻`）；`triage_diff --src` 校验，对不上或字幕更新过就拒跑（退出码 1）；**旧表只提示不拦**。`#35` 就此销号——三条里两条被本件收掉、一条没有凭据。
- **理由**：剧库 538 条里 132 条中文与清稿后不同，全部来自清稿前的 SRT，而旧表条数与列名一样、肉眼分不出。旧表不拒，是因为剧库手上还有 9 份，一律拒跑等于把人挡在门外——**闸变墙**。`#35` 那条「对稿→定档→审稿」没有可查凭据（`定档.md` 是手写的，mtime 说明不了什么），判据不清就硬做，只会留下一条拍脑袋的规则。
- **重开条件**：出现「配对表与字幕在同一分钟被改」的实例（校验精度只到分钟），那时加 hash。

## 2026-11-05

### 对齐不做一对多
- **结论**：一条中文挂 0 或 1 段英文；挂不上的留行、打标记交人，不自动拆合。
- **理由**：9 集双语轨实测 535 有英文 / 3 仅中文 / 0 仅英文，原制作者也是「中文当底、英文往上挂」。做一对多是自己加复杂度。
- **重开条件**：出现「一段英文必须拆给两段中文台词」且保真不可让步时。

### 判据 3 的可执行形态是「对白行未挂载 = 0」
- **结论**：不数「未挂载总数」，只数对白行；标题卡、组标、注释不计。
- **理由**：中文轨 538、英文轨 533，差的 5 条全是 4 张卡 + 1 条注释；而「≤3」这个 3 是双语轨维度「仅中文」的条数。两个口径混用会误判（11-05 已误判过一次「不过」）。
- **重开条件**：出现「英文轨确实漏了对白」的实例时，改判据为「真漏 = 0」。

### 人工定卡走 `--card`，不放宽识别规则
- **结论**：人工确认某条是卡，用 `--card <条号或文本>` 点名，标记写 `未配对:标识(人工)`。
- **理由**：短台词真漏（「是」「不」）和四字栏目名卡在机器眼里一模一样，放宽阈值等于放过一批真错。
- **重开条件**：同一部剧需要标 10 条以上人工卡时，说明识别规则该重做，不是继续点名。

### 「落地与复算」含 apply，不单列第五件
- **结论**：「验收复算」改名「落地与复算」，含「写进成品」+「复算」两段。
- **理由**：落地和验算是一件事的两端（改完立刻核）；单列会让「谁负责写进成品」含糊。
- **重开条件**：apply 与 verify 的使用者分化成两种人时再拆。

### 工具要在两部剧上跑过才算通用
- **结论**：只在一部剧跑通叫「凑合那一部」，不叫通用。
- **理由**：经验来自第一部剧，第二部剧是检验场——它专门暴露第一部没遇到的情况（简英分轨、双语轨就是在这儿才暴露的）。
- **重开条件**：第三部剧结构与前两部差异过大时，另立 profile，不动前两个。

### 分诊器的三条规则是被假红逼出来的
- **结论**：`triage_diff.py` 只留四条机器规则（比例过低 / 数字单向 / 整条未译 / 术语），删掉了「省略号=截断」。

### 分诊器必须能降级运行，不许把「有参照」写成必需
- **结论**：`triage_diff.py` 只有配对表就能跑；有参照才多判「T1 漏译」这一档，没有就明说判不了。
- **理由**：**能降级的工具有人用，只能满配的没人用。** 多数人手上只有一份字幕，要求先凑齐第二份参照，门槛高到当场劝退；而判不了的档位只要说清楚，人自己会补料。反过来如果为了「完整性」把参照设成必需，这工具就只剩我们自己用得起——那就没推广价值了。
- **重开条件**：某类用户的场景里，缺参照会直接判错（而不是判不了）时，再考虑强制要求参照。

### 交接不靠 handoff 装知识，靠「三份文件 + 一份目录」
- **结论**：知识分三处落盘（判定记录＝为什么、台账＝还差什么、工序＝怎么判），handoff 只写「读哪三份 + 现在到哪 + 第一件事做什么」。
- **理由**：2026-11-05 上一棒就是反例——handoff 只带状态、不带思考，接棒的人把「② 对齐」当成未开工又做了一遍。而 handoff 一旦为了「说全」写长，就变成历史复述，没人读（原库实测 142 行那份第二节就是「今天干完了什么」）。目录可以短，因为它指的地方是真的。
- **重开条件**：出现「某个决策既不属于任何文件、又必须传下去」的情况时，先给它找个文件，别塞进 handoff。

### 自检直接 import 工具，不起子进程
- **结论**：`tools/selftest.py` 用 `import` 调三个脚本的内部函数，不跑 subprocess。
- **理由**：子进程要落临时文件、抓 stdout 再解析，慢十倍且失败时看不出断言在哪；import 能一条条报「哪个用例、期望什么、实际什么」。三个脚本都有 `if __name__ == '__main__'` 保护，可以直接当模块用。
- **重开条件**：哪天某个工具改成纯 CLI（没有可复用函数）时，那个改回 subprocess。

### 归档区放 `docs/archive/`，不另开顶层目录
- **结论**：旧版方案、被否决的设计、一次性报告都进 `docs/archive/`，原位置留一行指针。
- **理由**：本库目录要干净到别人 clone 下来一眼看懂；多一个顶层 `archive/` 只会让人猜「这个和 docs 什么关系」。指针不能删——删了以后没人知道这事被处理过，过一阵会被重新提出来。
- **重开条件**：归档文件超过 20 份时，再按主题分子目录。

### 换行符护栏在本库恒绿，真防线是 `.gitattributes`
- **结论**：本库锁 LF（`* text=auto eol=lf`），工作区出现 CRLF 会被 git 静默归一，`git diff` 永远干净；`eol_guard` 恰好有一条豁免「HEAD 是 LF + 工作区是 CRLF + git 说没变 → 放过」（脚本第 104 行），在本库恒成立。**所以它在本库基本抓不到东西，别把它当防线，也别对外宣称能拦。**
- **理由**：11-05 反向实测——故意把 `docs/文档落点表.md` 写成 CRLF，`eol_guard --check` 报「一致」，`--fix` 报「还原 0 个」，只有手工改字节才回到 LF。
- **它还有用在哪**：`是大臣系列` 那种 `* -text`（禁转换）的库，以及「HEAD 是 CRLF、工作区被写成 LF」这个方向——那正是 2026-11-02 `.ass` 被写坏的样子，本库没有这类文件。
- **重开条件**：本库引入不经 git 归一化的路径（二进制、外部工具生成的大表）时，再给那类路径单独配规则。

### 同类错第 3 次，必须变成脚本，不许再靠自觉
- **结论**：同一类错犯到第 3 次，处理方式只有一种——写进 `selftest.py` 的用例、`doc_lint.py` 的检查、或 `.githooks` 的钩子。**不建经验卡目录、不靠提醒。**
- **理由**：本库的错几乎都能变成断言（超长、残留行、换行符、假红）。卡片要靠人读，脚本不用；而「制度没人遵守」这件事本身是负债——`日常杂活` 的 inbox 后来就没严格遵守。**能降级成脚本的规矩，别升格成制度。**
- **重开条件**：出现「写不成断言、只能靠人判」的经验，累计 6 条以上时，再考虑加一个中转页（不是目录树）。

- **理由**：它们服务的是「大量人判型活 + 多剧并行」的库；本库以脚本为主，踩坑的出口是判定记录一行 + 脚本注释一行，中转层只会多一层要维护的东西。

### 三道工序定名：机械修复 / 差异分诊 / 无参照通读
- **结论**：老名「查表 / 对轨 / 通读」在本库改为「机械修复 / 差异分诊 / 无参照通读」，三者在 `docs/工序-对稿.md` 第 7 节留映射；老名没有废，别的库照用。
- **理由**：① **老名按动作起，新名按输入条件起**——「有没有第二条参照轨」决定能判什么，动作名换一部剧就没人认得出；② 老名「对轨」被两样东西占着（工具②双版本对齐干的是对轨的机械部分，工序③干的是之后的判断），名字撞车；③ 改造之后发现原写法「有参照比对」**与工序内容自相矛盾**——这道工序设计上压根不要求参照（缺参照跑降级模式）。三条构词也统一成「限定语 + 动作」：机械｜差异｜无参照 + 修复｜分诊｜通读。
- **重开条件**：出现第三部剧的分诊形态与这两类都不同（如既有参照又有第三语种仲裁）时，另立工序，不改这三个名字。

### apply 与 verify 拆成两条命令，不合成一键
- **结论**：`land_verify.py` 有 `apply` / `verify` 两个子命令，各自能单独跑；apply 写完会自复算一遍，但复算也能拿任意两个文件单独跑。
- **理由**：**改的人和验的人不能是同一个动作**。合成一条命令等于自己给自己盖章——文件写坏了，同一个进程还按同样的假设判它对。拆开后，复算拿「改前 + 声明」重算期望值，不读 apply 的结论，所以能抓出「写错位」「多改一条」。
- **重开条件**：出现需要批量对几十集跑落地时，再加一条串联命令，但底层仍是这两条。

### 写回成品必须保持原编码，BOM 也算内容
- **结论**：写回用 `encoding_of(原文件)`，不统一写 `utf-8-sig`；复算加一条「BOM 状态不变」判据。
- **理由**：第一版一律写 utf-8-sig，文件的头两个字节变了——行内容一个字没变，diff 却显示第一行被改。**复算按行比看不出来**（BOM 在解码时已被吃掉），这类改动没人会注意到，但播放器认文件可能就变了。自测时抓到，否则就带着这个洞发布。
- **重开条件**：出现「输入 BOM、输出要求无 BOM」的成批需求时，加显式开关，不改默认。

### 双语字幕直切单独成一件工具，不塞进对齐器
- **结论**：`tools/bilingual_pairs.py` 专管「一份双语字幕（ASS/SRT）→ 配对表」，判卡直接 import 对齐器的 `kind_of`，不复制判据。
- **理由**：双语字幕里中英同一条时间码，**配对天然存在**，让它们走一遍时间轴匹配是多余的；混进对齐器会让「配对算法」和「解析格式」两件事缠在一起。分开后两边各自可验：双语轨直切在某一集出 538 条、有英文 534、候选 2 条，与对齐器走 9 集的结果完全一致。
- **重开条件**：出现「一份字幕里中英不同时间码」的双语形态（如英文单独延迟几帧）时，再考虑把它并入对齐器。

### 分诊器已在两部剧上跑过，R3 那档的阈值调不开
- **结论**：`triage_diff.py` 在第二部剧（成品的双语 ASS，3 集 2,348 条）跑出 7 条候选（3‰），数字规则**零误报**，说明归一化不是对着第一部剧调出来的。R3「比例过低」在两部剧都是低精度档：分布几乎重合（中位都 1.50、P01 都 0.78），而真漏（0.44）与「中文简洁」（0.50–0.57）落在同一段。
- **理由**：**没有阈值能切分这两个东西**——往上调会放过真漏，往下调会多报正常句。这解释了为什么修完 bug 后仍有 3/7 假红：它不是 bug，是这一档的固有精度。要提精度只能换方法（合并相邻两条看、或拿全片分布做离群），那是另一次判据决定。
- **重开条件**：出现「分句导致的假红占候选一半以上」且影响人扫读时，再评估「相邻两条合看比例」这条规则。

### 数字比对用「多读法」，不猜单读法
- **结论**：参照侧一个数字给出全部合理读法（`7.45` 既可能是 7:45 也可能是 7.45、`23.000` 是 23000、`10.00` 是 10），**任一读法对上就不报**；中文侧按亿/万分节（`3千2百万` = 3200 万），`7点45` 先并成 745。
- **理由**：9 集实测 25 条候选里 15 条是写法差异，全被同一条规则误报。猜单读法必错——数字在字幕里有千分位、时间、小数、量级词四种写法，没有一种能通吃。多读法不影响抓真错：`487` 对 `497` 没有任何读法能对上，照样报（有用例锁住）。
- **重开条件**：出现「多读法把真错放过」的实例（如中文写 9、参照写 9.75 还判不报）时，改成按语境取单读法，不再全给。

### 参照词数不数单个大写字母
- **结论**：`T.P.L.A.C.` 拆出的 5 个单字母不算词；`a` / `I` 照算。
- **理由**：缩写会撑大分母，把正常句压到 0.43 触发假红（9 集实测 1 条）。只排大写单字母，是因为排掉 `a` 会把「没着凉吧?」对 "Are you going to see a doctor?" 这类真错位一起放过——我第一版就排过头了，重跑时这条从候选里消失才发现。
- **重开条件**：出现「小写单字母被当词导致误报」的实例时再收窄。

### 接棒必读只当目录，60 行封顶
- **结论**：`docs/接棒必读.md` 加进 `doc_lint` 行数上限（60 行，ERROR 级）；里面只放「现在到哪 / 去哪查 / 第一件事 / 四条不许碰」，「别重做的事」「收工跑什么」「交接方法」一律换成指针。
- **理由**：它自己写着「只当目录，不装知识」，实际装了 4 处会持续长大的清单——坑一多就臃肿，臃肿了没人读完，目录就失效了。**上限写进脚本才算数，写在文档里等于没写。**
- **重开条件**：接棒必读需要容纳第二类读者（如外部贡献者）时，另开一份对外版，不撑大这一份。

### 机械修复只收「改法唯一」的规则
- **结论**：机械修复的准入判据是「说清改成什么，且换个人来改结果一样」；改法有两种的一律退回差异分诊或无参照通读。
- **理由**：体检报得出的三类事故里，只有内联标签残留能直接机改——粘连要拆词、金额问号要认币种，都是判断。把它们算进机械修复会让这道工序虚胖，也会让「机械段不参与判断」这条纪律失效。
- **重开条件**：出现可机判的拆词依据（词表或第二版英文交叉比对）时，再把粘连收进来。

### 改动清单同一条只能声明一次
- **结论**：`land_verify.read_changes` 遇到重复条号直接退出码 2；同一条的多处改动由判读环节先合成一行。
- **理由**：实测两段各声明同一条 → apply 报「应改 2 实改 2」、verify 报「声明 1 / 在位 1 / 多改 0」退出码 0，文件里只剩后一条，**复算全绿而少改一条**。旧库 §3.1 三坑之一「撞已有行号被 merge 静默丢」是同一个失效模式，所以这次写成断言，不写成提醒。
- **重开条件**：真出现「一条字幕必须分成两笔独立改动、且要分别验」的场景时，再改成累积式应用，但必须同时给 verify 换一套能测重复的口径。

### 词表是料，不属于任何一道工序
- **结论**：词表（专名 / 术语）是三道的共用输入，落在「准备」这一步。机器用法只有两处：机械修复拿「已见错写法 → 规定译法」直接替换，差异分诊拿「原文 → 规定译法」报 R6 嫌疑。人名 / 称谓表（谁是谁、怎么称呼、警衔）机器判不了，只当判读的背景料。
- **理由**：我上一轮把「通读前词表定稿」讲成词表属于通读，那是照抄老库的前置条件——那句成立是因为通读会让模型**产新译名**，不定稿就各译一套、事后整季重跑（S03 修 37 行译名）。而词表本身是校验用的料；绑在某一道上，另两道就名正言顺地不查了。
- **重开条件**：出现「同一部剧要维护两套词表（生成用 / 校验用）且内容常冲突」时，再拆成两份。

### 机械修复分两层，文件层的规则单列一份
- **结论**：机械修复含**文本层**（每条字幕的字符串）与**文件层**（整份文件的结构与样式：编码、画布坐标、样式表、字体字号、描边底纹、样式引用）。两层的判据装不进一份文档，规则明细另立 `docs/工序-清稿-规则清单.md`，每条标「改法唯一不唯一 / 谁来落」。
- **理由**：文件层不是「加几条规则」，是另一套输入（**样式基准**）和另一套落地——现有落地器只认「条号 + 旧文本」锚点，改不了 `[V4+ Styles]` 与文件头，还硬性要求行数不变，而增删样式恰恰改行数。硬塞进一份 130 行的文档，边界只会写成一句含糊话；上一版把机械修复缩成「格式线」，就是这么缩出来的。
- **重开条件**：文件层出现第二部剧要另一套基准时，把「基准」拆成独立示例文件，不动规则清单。

### PlayRes 的硬约束是宽高比，不是 384×288
- **结论**：画布坐标只要求两件事——非 0，且宽高比等于**视频的显示宽高比**（1080p 即 16:9）。数值本身随便，基准取 1920×1080 即可（720p 片源播放时等比缩到 0.667，字形不变形）。改画布必须同步缩放坐标、字号、边距、描边。
- **理由**：渲染时 x、y 各自按「视频尺寸 ÷ PlayRes」缩放，比例不一致字形就被非等比拉伸。实测老库成品（1080p 片源）写的正是 384×288（4:3）→ sx=5.0、sy=3.75，横向多放大 33%；他们自己说明里的「21 号实际渲染约 79px」= 21×3.75，说明当年只按 y 折算过。**这条拉伸是算出来的，没做画面截图。** 老库「PlayRes 硬约束 384×288」是历史处境（96 集 552 处坐标写死、不想动），不是通用判据——我在同一天把它抄成纪律，抄错了。
- **重开条件**：遇到片源本身是 4:3（老剧加黑边那种）时，比例要按**显示宽高比**算、不是按文件分辨率算；这条还没有实例，先记着。

### 样式器 v1 只做能断言的，两个开关不许猜
- **结论**：`tools/style_normalize.py` 做 F1–F5（头部、样式表、坐标与字号换算、编码保持）加 F7 引用断言；F6 内联标签统一、F8 底纹条删除只报不改。原文件 PlayRes 为 0 时必须 `--from-res` 声明，旧样式名对不上基准时必须 `--style-map` 给对应关系，缺一个就拒绝执行。
- **理由**：这两处正是「猜错也没人看得出」的地方——0×0 的稿子猜错坐标系就是整片错位；样式名对不上则全片静默回落 Default（第二部剧实测 698 条样式叫 `*Default`，基准里没有，不拦就一句话都不报）。F6 要判断「哪一段算英文」，F8 要判断「这条是不是卡」，都不是唯一解，所以只报。
- **重开条件**：出现带稳定 `中文\N英文` 结构的剧种（可机器切分语种）时，再评估 F6 自动化。

### README 上限从 80 放到 100，但不加机检
- **结论**：`README.md` 行数上限 80 → 100；**不加**「README 不许出现状态词」的机检。
- **理由**：80 是落点表里的**初值，没有任何事故依据**（接棒必读那 60 行才是被事故逼出来的）。工具表每加一件 +1 行，6 件就顶到 80/80，剩下的空间只能靠把说明压成黑话换。想加机检那条也放弃了：README 里两处出现「进度」，都是**指针**（「进度看台账」），机检会照报，误报一多整条检查就没人看。写不成断言就不硬凑成制度。
- **判据**：上限要宽还是紧，看这份文档是「清单型」还是「判据型」——清单型（工具表、规则清单）随件数线性长，长的是必要信息，上限该宽；判据型（工序、做法）一长就说明判据在堆，该拆或该删，上限该紧。
- **重开条件**：到 100 行还紧，先砍「目录」和「已知不足」两节（它们有更合适的真身），不再往上调数字。

### 无参照通读立起来：判据三段 + 只两档，且机判项为零
- **结论**：`docs/工序-审稿.md` 只留两档（应改 / 不改），命中项按 C1 理解反 / C2 看不懂 / C3 剧情断 三段十四项，另设十二类「不报」与七种形态；**这道工序的机判项为 0**，机器只做切片、预筛、密度统计。
- **理由**：两档是被实测逼出来的——「可改可不改」过吃掉一批人工判量的四成，落到成品观众看不出来。十二类「不报」必须和命中项一起写，只写命中项的后果是「真问题被措辞噪声淹掉」（老库一批 16 条复核里 4 条是抽样片段掐头去尾的假阳性）。机判为 0 这点要写明，否则下一手会去写规则替代它，而规则替代不了「观众会不会理解错」。
- **重开条件**：出现可机判且实测假红低于两成的条目（如话轮标记个数、数字量级）时，可以把那一条从人判挪到机器挑候选，但保留人定案。

### 词表怎么攒：机器挑候选、人定译、只收会重复出现的
- **结论**：提取交机器（`tools/term_candidates.py`：挑大写专名与缩写、计次、给首现位置和同条中文片段），定译交人；只收出现 ≥2 次的；一个词只填一个规定译法，错的写法进「已见错写法」，两种都合法的写备注。
- **理由**：老库压根没有「提取」这一步——术语表是人手写进 `proof_rules.py` 的常量，`build_terminology.py` 只负责导成 JSON；换一部剧就得凭记忆重新想一遍，那正是接新剧最费神的地方。实测 38 集参照版跑出 80 条候选（≥25 次），人名、机构、缩写都在，假红只剩片段词与称谓。
- **重开条件**：机器挑出来的「大写普通词」占候选一半以上时，加词典白名单，不上语种模型——这一步要的是省人工，不是判得准。

### 落地分两次，但配对表要在机械段之后重建
- **结论**：机械段单独落一次盘，分诊段与通读段并成一张再落一次；**机械段落盘后必须重建配对表**，然后才跑分诊。
- **理由**：机械段必须先落，因为分诊要吃干净输入（脏输入让假红成倍）；不能全并成一次落，因为两张清单改同一条时后行会静默覆盖前行、而复算照样全绿（已实测）。另一半是刚发现的：配对表里存着中文原文，机械段一改它就过期，而分诊只读表不读字幕（`triage_diff.py:59` 只认「中文条号 / 中文文本 / 英文文本」），照着旧文本出的候选，落地时锚点必然失配——不是改错，是白跑一轮。
- **重开条件**：分诊改成直接读字幕取中文原文（不再信表里那一列）时，「重建配对表」这条硬步骤可以撤掉。

### 命名依据要从「按输入条件」换成「按职责权重」
- **结论**：2026-11-05 定的三道工序名，依据是「有没有第二条参照轨」（见 `docs/工序-对稿.md` 第 7 节）。这个依据只解释得清两道各自成立，解释不了**哪道是主线**。下一轮改按职责权重定名：前置两道服务主线，主线一道定成败，名字跟着层级走。
- **理由**：工作量与影响不成比例——旧库 S03 机械段 1149 条里 987 条是格式线（86%），一条错译都没抓到；E04 补的 43 处里一半是通读抓的。对外报「工序 3/3 道齐」会让人以为三道权重相同，实际是两道清场、一道定成败。更直接的问题：「无参照通读」这名字把**主线命名成了降级模式**，读者第一反应是「没有参照时的备选」。
- **重开条件**：出现第二道也能判「观众会不会理解错」的工序时，主线不再唯一，按新的分层重排，不硬塞进这套三层结构。

### 流程按职责重排：清稿 / 对稿 / 审稿，审稿是主线但强度可变
- **结论**：三道工序改名为清稿（依据规则）、对稿（依据参照）、审稿（依据判断）。审稿前加「定档」一步——它不是独立工序，是审稿第 3 节：来源先验 + 抽 40 条（三段均分，1 条硬伤即转全量）+ 对稿候选数只单方向，产出「全量 / 关键点」两档。档位写进 ASS `Title` 与剧库 `定档.md`。
- **理由**：旧三级（查表 / 对轨 / 精读）按输入条件划分，把三道拍成一样重；实测工作量与影响成反比——S03 清稿 1149 条里 987 条是格式线，却一条错译都没抓到，而 E04 逐句读补的 43 处里一半是意思错。分档依据是**输入质量**而非流程进度，所以「质量好就少读」成立；但它省的是约 70% 不是 100%——抽样本身要半小时，且来源是机翻时一分不省。
- **重开条件**：出现第二道能判「观众会不会理解错」的工序时，主线不再唯一；或抽 40 条实测误判率高于两成时，改抽样口径（加抽或改按段落抽）。

### 命名体系定四级，一域一套词

### 中英间距只管拉丁字母，数字不补空格
- **结论**：MT3 的「中英之间补空格」只在中文与**拉丁字母**之间补；中文与数字之间不补。半角标点换全角的触发条件是「前一个是中文，且后面是中文 / 行尾 / 空格」，任一侧是数字就不换。

- **结论**：`examples/样式预设/` 出三档——细边（中文 4/2、英文 3/1）、常规（6/3、4/2）、厚边（8/4、8/4），各附一张自造词样张；`MF5` 判据从「边 2 影 1」改成「按选定预设」，选哪档由人定。

- **重开条件**：出现第 2 个病根装不下的新形态，那时加一节病根，不加回逐条判词。

### 改闸的退出码等于改所有调用方的行为

- **结论**：`eol_guard` 的「检查 0 个」改退 2，必须同时把调用方全跑一遍——`pre-commit` 是逐文件跑的，于是每个新增文件都被判红、提交直接拦死。
- **理由**：返回值是给调用方看的，不是给自己看的，钩子 / `selftest` / 别人的脚本都算调用方。这次真正错在把「库外没查」和「库内新文件没得比」混成一个数；修法是分开计数（库外退 2、新文件退 0），不是取消闸。
- **重开条件**：无（已修，`selftest` 三条用例锁住这两个分支）。

### 跨库假警只对老库语境跳过，不是无条件跳

- **重开条件**：出现「本库文档真需要引用隔壁库同名目录」的实例，那时改成白名单，不改成无条件跳过。

# 字幕验收复算（subtitle-check）

> **举证与实测数据**：`docs/工序-验收-实证.md`——每条规矩为什么长这样、阈值从哪来、哪次踩了什么后果。**改规矩前先读它**；它是规矩的依据，不是规矩本身。含真实集号，只留本地。

> **⚠️ 两个 `accept.py` 不是同一个，跑错不会报错、只会给你一堆看不懂的数字**
>
> | | 在哪 | 验什么 | 接口 |
> |---|---|---|---|
> | **本技能说的** `accept.py` | **不在本库**，只在派活单给的上游工具目录 | 执行方交回的 **findings**：七项（findings 总数 / inserts 总数 / 时间轴倒序 / cn 逐字 / evidence 出处 / 机械段清单…） | `--season S0x --expect-findings N --expect-inserts M` |
> | **本库** `tools/accept.py` | 本库 `tools/` | 落地后的**成品结构**：条数 / 对白行 / BOM / 改动数 / 补行位置 / 落盘密度 / 定档痕迹 | `python tools/accept.py <改前> <改后> --changes <表> [--inserts <补行>] [--stage <定档.md>]` |
>
> 两者验的东西不重叠，同名是历史原因。**验 findings 用前者（本库没有），验成品用后者（本库有）。**

对一批交付做程序化验收 + 人工复算，给出放行或打回。**改的人不验，验的人不改**——写这批 findings 的人不用本技能给自己验收。

通用纪律只在一处：`docs/判断纪律.md` 技能（动手前先加载它）。

## 干什么（两分钟出结论）

验收要跑的是**两件事**，本库只做得了其中一件。先把界线分清，再动手。

**① 验成品结构——本库一条命令**（条数 / 对白行 / BOM / 改动在位 / 补行位置 / 落盘密度 / 定档痕迹）：

```bash
python tools/accept.py <改前> <改后> --changes <改动.tsv> [--inserts <补行.tsv>] [--stage <定档.md>]
python tools/land_verify.py verify <改前> <改后> <改动.tsv> [--inserts <补行.tsv>]
```

`accept.py` 内部已经调 `land_verify.verify()`，所以第二行是**单独复核落地**用的，不是每次都非跑不可；改动人自己跑过 `apply` 的，这里必须再跑一次 `verify`（改的人不验这条不打折）。**两份都是逐集比，没有全季开关**——整季就先逐集跑、再合计。退出码非 0 即不过，别只看输出里有没有红字。**`verify` 的改动表 / 补行表至少要给一个**，两个都不给会直接以退出码 2 退出（提示「既没有改动表也没有补行表，没有可落地的内容」）。

**② 验 findings 七项——本库没有这个工具**。手册第 33 行那张表里「本技能说的 `accept.py`」（带 `--season` / `--expect-findings`）只存在于派活单给的上游工具目录，本库 `tools/accept.py` 同名但验的东西不同。七项在本库的真实覆盖：

| 七项 | 本库覆盖情况 |
|---|---|
| 1 findings 总数 / 2 inserts 总数 | ❌ 只能人工数，或跑上游那份 `accept.py` |
| 3 成品行数差 vs inserts | ✅ `tools/accept.py` 的「条数 / 对白行」两行 |
| 4 时间轴倒序 | ⚠️ 只查补行前后邻居（`accept.py` 「补行位置」），**全文件行序不查**，理由见 `accept.py::inserts_position_ok` 注释 |
| 5 cn 与源文逐字不一致 | ✅ `land_verify` 四重定位会报「旧文本在改前就找不到」 |
| 6 evidence 为空 / 7 引文查无出处 | ❌ 本库没有 findings 层的 evidence 校验，只能人读（审稿链里的 `validate_semantic.py` / `isolate_review.py` 有 evidence 字段，但那是审稿结果，不是 findings） |
| 8 机械段清单 | ❌ 只能人读 |

**没有工具覆盖的项不等于可以不查**——那几项就是本手册下面几节要人做的部分。

## 七项 + 一项怎么读

| # | 项 | 红了先想什么 |
|---|---|---|
| 1 | findings 总数 | 与期望差太多 → 有漏写/多写，或期望本身过期 |
| 2 | inserts 总数 | 同上 |
| 3 | 成品行数差 vs inserts | **落地前必红**（补行还没进成品）——先分清时序，不是错误 |
| 4 | 时间轴倒序数 | 只报「成品比源新增的倒序」；源自带倒序（S01E01/S02E01/S02E02）不算错 |
| 5 | cn 与源文逐字不一致 | 执行方抄错 `cn` → 打回该条 |
| 6 | evidence 为空 | 违反证据纪律 → 打回该条 |
| 7 | evidence 引文查无出处（官方 SRT 与源字幕英文**都**没有） | **疑似编造依据** → 打回该条并要求重写 evidence。注意：引我们自己的错文是**合法**证据（技术缺陷类改动只能这么写），只要能在源字幕该集英文里找到 |
| 8 | 机械段清单 | evidence 前缀为「译名统一/规范用字/补语误写」的自动改动，**逐条人读**后才放行。**先扫「长度差」列，超 ±30% 必查**（改错别字不会掉一大截） |

## 报红四分清（别急着判谁的责任）

对上任何红项，先问是哪种：

1. **时序**：还没落地就跑了验收（第 3 项典型）→ 等落地再验
2. **期望过期**：拿旧批次期望条数验新批次 → 核对 `--expect-*` 参数（**那是上游那份 `accept.py` 的参数，本库没有**；本库换成「核 `--changes` / `--inserts` 表里的条数是不是这一批的」）
3. **阈值 / 口径设错**：用默认阈值跑出「全绿」，但项目红线更严 → 显式给项目红线，别用默认。本项目红线是 `--max-bytes 2048`，而 `procedures_audit.mjs` 默认 3072（宽一半，注意它在另一层目录、不在本工具目录下）；2026-10-26 用默认值跑，三张卡全部超限却被报「全绿」。**本库没有 `procedures_audit.mjs`**，这条是上游的教训，搬过来是为了记住「默认阈值比红线宽」这件事，不是让你在本库找这个脚本
4. **脚本自己错**：季节前缀取错、路径拼错，报红冤枉执行方 → 现象记 `台账`（卡库：`工具-报红先分清真错与时序.md`）

前四类都排除仍然红 → **这才是真错**，这时候才去追责任。

## merge 丢弃数必须看（2026-10-27 教训）

> **本库没有 `merge`**（两张清单并成一张靠人工，见本文开头对照表）。这一节留下的是**口径**不是命令：**并表前后条数必须对得上，少了哪条要说得出原因**。没有工具帮你数，就自己在并表前后各数一遍。

`merge` 首次跑出「保留 N 丢弃 M」时，**逐条看丢弃原因**。不能只看「0 被拒」就放行——被 merge 丢弃的条目压根没进 patch，`apply` 无从拒绝，永远显示 0 被拒。

**三个数字一起看**：findings 条数 → merge 保留数 → apply 应用数，任一环节少都算问题。

| 丢弃原因 | 怎么修 |
|---|---|
| 时间码不符 | finding 的 `tc` 抄错 → 从 `必看.tsv` 抄源文真实时间码，别自己写 |
| 行号不存在 / cn 不符 | `ln` 或 `cn` 抄错 → 回源文逐字核对（含空格） |

**`verify` 绿 ≠ 所有改动到位**：它只校验 patch 内的条目，被丢弃的那条它不知道存在。要确认某条真进了成品，按 `en` 去成品里搜那一行。

丢弃表基本等于「执行方的抄写错误清单」（很少是规则问题），所以它同时就是打回证据。

## check_all 各组的读法（落地后跑）

> **本库没有 `check_all.py`**（八组一次报全的那个）。替代是两条命令，合起来覆盖不了全部：
> `python tools/selftest.py` 对 T/K/X（单测、术语表与规则表同步、两张表把同一个词映射到不同目标）；
> `python tools/accept.py` 对 I/V 里与成品结构有关的部分（BOM、条数、对白行）。
> **H（扫描指纹）、E/F/S/K′（集数覆盖、findings-补丁对应、补丁过期、术语残留）本库没有对应工具**，这几组只能人查。下表当检查清单用，不是命令清单。

| 组 | 查什么 | 不通过典型原因 |
|---|---|---|
| T / K | 全部单测、术语表与规则表同步 | 改了规则没改测试；改了 NAME_MAP 没跑 build_terminology |
| X | **判据表互相冲突** | 同一个词在两套表里映射到不同目标（#77/#78/#79 全是这一类） |
| H | 扫描指纹 | 规则改动导致扫描变化——**属预期就 `--update-fingerprint`，不属预期先查清再刷**（台账 #70 即此） |
| I / V | 不可见字符、成品校验 V01–V21 | 混进 BOM/零宽字符；结构坏、句群只改一半 |
| E / F / S / K′ | 集数覆盖、findings-补丁对应、补丁过期、术语残留 | 某集没做却说做完了 |

**别在本文写死组数或单测例数**——它们每加一条检查就变，写死的数字必然过期，而过期的文档比没写更坏。

## 读外部 TSV 的防呆（执行方交回的判定表）

- 一律 `encoding="utf-8-sig"` 读——带 BOM 的表会让首列名变 `"\ufeff集"`，**整表静默失效、一条都不生效**（2026-10-27 S08，66 行全空跑）。
- 读完 `assert 行数 > 0`，别只信「读成功了」。

## 放行标准（全满足才放行）

1. 七项全绿（或红项已用四分清解释且属时序/期望/阈值问题）
2. 第 8 项机械段清单逐条读过
3. `verify` 通过
4. merge 丢弃条数为 0，或每条丢弃原因已查明
5. 简报三件齐全、疑问表里没有悬而未决的「交回统筹」项

## 不满足就打回

打回时给执行方三条信息：哪几项红、每条的行号与原因、重写要求（如「补 evidence」）。**不替执行方改 findings**——改的人不验，验的人不改。

## 独立第二方判读的触发（本技能是验收方视角时）

满足任一条就建议开副会话复判：单批判断量 ≥ 50 条 / 要给出「整批不用看」的批量结论 / 判据要跨季复用。程序能判定的（跑规则、merge、apply、verify）不需要第二方——**验收复算本身就是第二方**。

## 一条元原则

**会报错的检查才值得信。** 改过或新增任何检查后，先故意造一个错看它认不认；认不出的检查等于没有。这条对 accept 七项、check_all 每一组、卡库里的工具卡同样适用。

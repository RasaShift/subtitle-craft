## 2026-11-09

### 外部技能只装原版；术语表只收出过事的词

- **结论**：全局装 `writing-for-agents` + `diagnosing-bugs`，都取上游原版，只改 `description` 指向本库真实路径，正文一字不动；中译版不装，本地 `_research/` 留作对照。`docs/GLOSSARY.md` 只收 4 个已被误用或跨库会看错的词，**不收「薄壳」这类被否决过的生词**。
- **理由**：中译版正文 47 处核心术语留英文（`pointer` 18 / `branch` 11 / `leading word` 8），半中半英不比纯英文省力；且中译仓库自己还在改 README、发 npm 插件，混进非翻译产物。术语表真正的风险是「收进去的词变成必须记住的生词」——11-07 起名「薄壳」被当场问「这是什么意思」，八份技能抬头全改回人话，同一个错不犯第二次。
- **重开条件**：上游出现本库用得上的新技能，或某个词被两个库理解成两个意思——那时才动这张表。

### 术语表只写词义，不抄会过期的状态

- **结论**：`docs/GLOSSARY.md` 词条区不许出现状态词（`下一批` / `目前` / `现在` / `当前` / `还剩` / `暂时` / `最近`），`doc_lint` 的 `check_glossary_state` 查；号段、进度这类一律指向真身，不写当前值。
- **理由**：建表当天就从协议抄了一句「下一批从 `#12` 起」，抄的时候对、抄完立刻过期（台账已排到 `#41`）。**术语表里给一条错的规则比不给更糟**——人是来查「这词到底什么意思」的，不会去核对号段。同源于 `GQ-17`「转述丢条件」：副本不知道原件已经变了。
- **重开条件**：某个词的定义本身必须带时间限定（比如「旧编号」这种相对说法）时才放宽——那时写清参照点，仍然不写绝对号段。

### 跨库编号按来源分家，一个问题只用一个号

- **结论**：`GQ-n` 专给「剧库报本库的问题」，从 `GQ-19` 起；**同一个问题两边沿用同一个号，不在两边各起一个**——剧库报的记 `GQ-n`，本库台账里记它**也用 `GQ-n`**。裸 `#n` 只给本库自己发现的待办，不跨库。`#1`~`#12` 是 2026-11-08～09 的中期编号，**封存不改**。
- **理由**：裸 `#n` 三套并存且互相撞——剧库 `06_治理/待办台账.md:31` 的 `#10` 是「38 集一致性比对」、同目录 `待报通用库.md` 的 `#10` 是「DR 规则」、本库台账 `#12` 是「关键点核预筛」而剧库报来的 `#12` 是「给人看的文档没有形态」。**同一符号指四件事**，看协议时无法判断。改旧号不行：剧库 `06_治理/` 有 47 处裸 `#n` 引用，改了全断，与本库「编号是身份证不是顺序」直接冲突。**「两边各起一个」是新长出来的同一个病**：骨架形态那条一开始本库起了 `#42`，于是同一件事上挂着三个号（剧库 `#12`、本库 `#42`、该用的 `GQ-19`），搜哪个都不全——2026-11-09 当场改回 `GQ-19`。
- **重开条件**：出现「必须把两套编号合并成一套」的硬需求（比如做跨库总索引）时另立映射表，**仍不改编号本身**。一旦有人为了好看把 `#1`~`#12` 重编成 `GQ-19`~`GQ-30`，说明这条被推翻了。

### 台账按「卡在谁身上」分节，不按内容也不按进度

- **结论**：分节只用一个维度——`等我动手` / `等协作方` / `等外部` / `等你拍板`；一条同时等两样的，归到**先动的那一方**；「现在手上」这类摘要不占节，压成顶部一句。这套搬到任何库都成立。
- **理由**：11-09 当天先按内容切过四节（本库要改的 / 等真实数据验的 / 等外部条件的 / 等场景触发的），**四节混了四个维度**（谁动手 / 到哪一步 / 阻塞原因 / 触发方式），跟 11-08 废掉「三档」是同一个病——三把尺子。按内容分还有第二个毛病：换库就失效，剧库没有「本库要改的」这种类。按进度分更糟，同一条会在档位之间来回跳。
- **重开条件**：出现「阻塞方超过四方」的场景（比如引入第三方验收），那时加第五方，**仍不改维度**。

### 扫除三项不做：文件大小钩子 / 合并件数 / 补 AGENTS.md

- **结论**：① **不装 20KB 提交钩子**——9 个存量文件超标（判定记录归档 124KB、`selftest.py` 81KB、审稿手册 50KB、`doc_lint.py` 37KB 等），全是该大的账本和工具本体；本库按文件类型管行数（`doc_lint` 的 `LIMITS`），统一字节阈值不适用。② **不合并「30 件 / 25 件」三处写死**——`doc_lint.py:553` 的 `check_counts` 已拿三处跟 `tools/*.py` 实际数对，写错报 ERROR；收成一处反而让对外文档没具体数。③ **不压 README、不补 AGENTS.md**——README 109 行是对外说明；agent 入口是 `docs/接棒必读.md`（60 行纯目录），职责已覆盖。
- **理由**：三条共同点，是拿「代码项目的通用做法」套文档库。文件大小阈值假设「大就是该拆」，本库大的是账本；AGENTS.md 假设「入口缺失」，本库有更严的 60 行目录。
- **重开条件**：本库开始产出真代码（不只是单文件脚本）时，第①条重判。

### prove-it 三条只收一条：拒「靠人一眼看见」

- **结论**：电脑管家库建议吸收 `prove-it` 三条，只收「结构上犯不了」和「拿真错撞」，**拒掉「让人一眼看见」那一档**——它跟 `docs/做法.md` 三级阶梯表里 ✗ 行（「要靠人读才算生效的东西，等于没有」）直接冲突。
- **理由**：三条里一条已被 `docs/做法.md:33` 的判据覆盖（规则配拦截），一条与本库既有判断打架，只有「结构上犯不了」是真缺——本库最强只到「钩子拦截」，那是犯了再拦，没有「根本写不出来」。
- **重开条件**：出现「结构上做不到、自动检查也做不到、但人一眼能看出来」的场景时重判。

### 「拿真错撞」收进第 6 步：正例必须来自真错

- **结论**：`agent-craft` 第 6 步在「验双向」后面补一句——**「该命中的」那一半，正例必须是历史上真犯过的错，不许自己编**；把真错原样放回去，检查不红就说明这条检查是摆设。不加「让人一眼看见」那档。
- **理由**：第 6 步原文只防**误伤**（造一条不该命中的反例，看会不会乱报），缺的是**空转**——检查写了、看着全绿，其实从来没真跑过。自己编的正例和检查逻辑同源，自己验自己必然过，所以「验过」既不等于「验对」也不等于「真跑过」。**落地第一分钟就撞出活标本**：`doc_lint` 的件数核对不认 `接棒必读:17` 那种表格写法（改错退出码仍为 0），记 `#46`。
- **另一条边界**：`agent-craft` 是全局软链，改一次四个库同时生效，属跨库改动——这次是用户 13:32 单独拍板才动的，不能当本库小活顺手做。
- **重开条件**：出现「正例没法从历史里取」的判据（全新领域、没有真错可放）时才放宽成「用最接近的真实失败」。

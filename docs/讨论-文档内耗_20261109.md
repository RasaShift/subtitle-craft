## 二、讨论走过的四轮

### 第一轮：上限太硬，能不能放宽

**用户提议**：警告保留但不每次改；或者超 20% 才改，改就改回上限的 70%–80%。

**当场的判断**：
- 「警告不必等于必须改」——对，这是真问题。
- 「超 20% 改回 80%」——**不能做**。它把「搬走一块」变成「必须砍够 30%」，而要凑数字时最先砍掉的往往不是废话，是判断依据。当天压日志时就差点把「宁可漏报边界也别给假 WARN」整句删掉。
- 我提的方案：超限降 WARN、超 20% 才 ERROR、余额提示、收工统一清。

**这一轮方案后来被自己否掉了**，理由见第四轮。

### 第二轮：根因不是上限，是落点太多

把当天的「改文档」动作拆成两类：

- **A 类：写新内容**（判定记录加一条、协议加一条广播）——有价值的生产
- **B 类：把同一件事同步到第 2 到第 10 个地方，然后各自压回去**——纯损耗

B 类占六成以上。实例：「审稿降为可选」这一件事，改了 10 处：

`工序-审稿.md`、`接棒必读.md`、`README.md`（两处）、`做法.md`、`流程总图.md`、展示页、`subtitle-read` 技能、判定记录、`CHANGELOG.md`、协议 §4、日志。

**其中真正需要独立写内容的只有 2 处**：`工序-审稿.md`（判据真身）和判定记录（决策真身）。其余 8 处是「因为那里也提到了工序，所以得跟着改」。

**结论：内耗的根不是上限，是同一批事实有多个落点。**

### 第三轮：各司其职是不是话术，挪文件有没有用

**用户的质疑（两条都成立）**：

1. 「每一处都有用、各司其职」是不是在用不同的理由说服自己制造新文档？
2. 挪文件到底顶不顶用？东西总量没变，只是位置变了。指针又有什么用——指过去不还得读？

**判断**：

- **各司其职一半是话术。**
  - 真需要分开的：手册 vs 判据（一个讲步骤，一个讲条目，内容完全不重叠）。
  - 假需要的：`README` / `接棒必读` / `流程总图` / `做法`——**四份都在说「工序有哪几道」**，同一批事实说了四遍。
- **挪文件确实不减少总量。** 它唯一改变的是「**每次干活必须读的量**」。
  - 判定记录 124 行，新会话不需要全读，只看 15 行索引。
  - 如果这 124 行塞在接棒必读里，就是每次多读 124 行。
  - **所以「挪」的正当理由只有一条：这份内容不会被每次读到，却占着每次都要读的位置。**
- **指针的价值不是「减少阅读」，是「降低遗漏」。** 但如果指针指的东西读者每次都要读，那指针就是脱裤子放屁——应该直接放在原地。

**当天一次具体的挪错**：定档样例从 `工序-审稿.md` 挪到 `examples/新剧接入.md`。它是「要写定档文件的人当场就要看」的内容（第 1 级），挪走只因为塞不下——**这是分类错误被行数上限逼出来的搬家**。

### 第四轮：外部参考（mattpocock 技能包）

参考位置：`E:/Workedbuddy/电脑管家/.workbuddy/_research/skills`。

读的五份（全在外部库，绝对路径）：`E:/Workedbuddy/电脑管家/.workbuddy/_research/skills/.agents/writing-docs.md`、`E:/Workedbuddy/电脑管家/.workbuddy/_research/skills/docs/productivity/handoff.md`、`E:/Workedbuddy/电脑管家/.workbuddy/_research/skills/docs/productivity/writing-for-agents.md`、`E:/Workedbuddy/电脑管家/.workbuddy/_research/skills/skills/engineering/retro/SKILL.md`、`E:/Workedbuddy/电脑管家/.workbuddy/_research/skills/skills/engineering/domain-modeling/SKILL.md`（含 `ADR-FORMAT.md` / `GLOSSARY-FORMAT.md`）。

**学到的东西，按重要性**：

#### 1. 三种病有了名字

`writing-for-agents.md` 原文：

> Pruning: single source of truth, relevance, and the no-op test applied sentence by sentence, against **duplication**, **sediment** and **sprawl**.

| 病名 | 我们这儿的样貌 |
|---|---|
| **duplication**（重复） | 工序事实写在 README / 接棒必读 / 流程总图 / 做法四处 |
| **sediment**（沉积） | `接棒必读:42` 那行，11-08 与 11-09 的结论一层层叠上去，从没清理 |
| **sprawl**（蔓延） | 一个工序拆成主干 / 判据 / 手册 / 实证四份 |

有了名字以后遇到直接对号，不用每次重新描述。

#### 2. 为什么「撞上限就压字数」——因为工具只看得见行数

`writing-for-agents.md` 原文：

> **"I asked an agent to trim a document and it cut the functionality."**
> Agents told to "streamline" optimise for **length**, because length is the thing they can see.

它给的替代判据叫 **no-op test**：

> delete the line and ask whether the agent's behaviour changed.

**删掉这行，读的人（或 AI）的行为会不会变？不变就是废话，整句删。**

配套一句更狠的：

> When a sentence fails, **delete the whole sentence rather than trim words from it**.

**整句删，别改词。** 改词效果最差——结构没变，下次照样撞。当天压日志干的就是改词。

#### 3. 两种负载：指针为什么不是「还得读」

`writing-for-agents.md`：

- **Context load**：每轮常驻、不管用不用都要付的钱（常驻文件的一行、技能 description）
- **Cognitive load**：记住「有哪些文档、什么时候用」的钱

**「指过去不还得读」混淆了这两笔账。** 指针成本是 context load（一行，每轮付一点点）；通读成本是 cognitive load（只有真需要时才付）。

`接棒必读:42` 那 900 字符之所以是错，不是因为长，是**把「偶尔要用」的东西放进了「每轮付钱」的那一层**。

（一条不适用：原文说「不要试图最小化 cognitive load，那是人类能动性的代价」——这条对我们不成立，我们靠文件记不靠脑子记。）

#### 4. 挪文件的正确姿势叫 progressive disclosure

> **Information hierarchy**: the ladder from in-file step, to in-file reference, to **disclosed reference behind a pointer**. Progressive disclosure is moving material down that ladder so the top stays easy to read.

三级是固定位置，不是随便挑一个文件：
1. **文件内步骤**（就在这儿，直接读）
2. **文件内引用**（同一份文件里指一下）
3. **指针后面的按需披露**（另开一份，需要才打开）

**判断该不该挪，看它属于哪一级，不看还剩几行。**

#### 5. 唯一能真正治「同步十处」的做法：从不复制

`handoff.md` 原文：

> It deliberately does not carry anything already written down. The document **references specs, plans, ADRs, issues, commits and diffs by path or URL, and never copies them**. That keeps the file small, and it keeps the settled detail **in one place instead of two copies that drift apart**.

**「从不复制」是它的设计前提**，理由：定下来的细节只存一处，不产生两份会互相漂移的副本。

我们的库里复制是默认动作。**每次改都要同步十处，不是勤快，是欠债。**

#### 6. 「什么时候该放常驻层」有一个可判的问题

`handoff.md`：

> **"When does something belong in `CLAUDE.md` instead?"** Ask whether it's **true next month**.

- 成立 → 常驻层（`CLAUDE.md` / 我们的 `MEMORY.md`）
- 一次性的活 → handoff（我们的日志、台账）

`接棒必读:42` 那行里：「11-08 那天台账剩 2 条」下个月不成立；「判据要事前可判」下个月成立。**两种混在一行里，谁也挑不出来。**

#### 7. ADR 可以被我们复杂得多

`ADR-FORMAT.md` 原文：

> That's it. An ADR can be a single paragraph. The value is in recording *that* a decision was made and *why*, not in filling out sections.

写 ADR 的三条件（三条全成立才写）：① **难以逆转** ② **没有上下文会让人困惑「当时为什么这么干」** ③ **是真的权衡过**。

对照我们的判定记录：一条标题 + 结论 + 理由三四条 + 重开条件 + 索引一行。**比它复杂，而且复杂出来的部分没人读。**

#### 8. 术语表缺一个字段

`GLOSSARY-FORMAT.md` 的格式：

```
**Order**:
{A one or two sentence description}
_Avoid_: Purchase, transaction
```

**我们只有「定义 + 在哪」，没有「别叫什么」。** 而「别叫什么」恰恰最有用——当天刚判过「一词二义」。

## 三、定下来的结论（十条）

| # | 结论 | 理由 |
|---|---|---|
| 1 | **上限值不动**（130 行 / 900 字符 / 60 行） | 这些数代表「一页能读完」，放宽等于自欺 |
| 2 | **不做分级降级**（超限 WARN、超 20% ERROR） | 会掩盖信号，而信号是唯一提醒「这里有重复」的东西 |
| 3 | **不做「超 20% 改回 80%」** | 把「搬走一块」变成「必须砍够 30%」，凑数字时先砍掉的是判断依据 |
| 4 | **不做「收工统一清 WARN」** | 把「当场发现重复」变成「攒着以后处理」，攒着就会忘 |
| 5 | **撞墙按三步诊断**：① 这段是不是在复述别处（是→删细节留名字）② 该归档的有没有归档（该→搬 `archive/`）③ 都不是，才谈压缩或拆卷 | 当天三次撞墙，两次栽在第①步，一次在第②步，没有一次到第③步 |
| 6 | **拆卷判据从「超行数」改成「有没有另一批读者」** | 没有另一批读者、只是塞不下，正确动作是删内容或改写法，不是拆文件 |
| 7 | **根因是「同一批事实有多个落点」**，不是上限 | 一件事改 10 处，真正需要独立写内容的只有 2 处 |
| 8 | **`buddy-workflow` 该删** | 41 行内容 100% 被 `MEMORY.md` 覆盖（输出偏好、多库分工），唯一独有的 Obsidian 双链一年用不到几次 |
| 9 | **`agent-craft` 的「开局加载」时机错了** | 199 行里 90% 是施工细节（验双向、拿真错撞、断言定位），只在改工具 / 写检查 / 做验收时用；核心六条早已在用户记忆里 |
| 10 | **`接棒必读` 可以解散** | 它现在装了两样性质不同的东西：导航（下个月还成立）+ 状态（一次性）。按 handoff 的判据，前者进 `MEMORY.md`，后者进台账 |

## 四、被否掉的方案（连理由一起留着）

| 方案 | 否决理由 |
|---|---|
| 超 20% 才改、改回 70–80% | 逼人砍内容凑数，砍掉的先是非废话 |
| 分级告警（超限 WARN / 超 20% ERROR） | 掩盖「撞墙 = 有重复」这个信号 |
| 收工统一清 WARN | 攒着处理必然忘，`做法.md` 里「靠自觉的东西等于没有」 |
| 余额提示（剩 ≤5 行时列出） | **不是错，是缓办**——它只让撞墙提前知道，不解决为什么撞 |
| 用 `wayfinder` 整套替换台账 | 它长在 issue tracker 上，我们没有 tracker；只借它一条概念：「map 是索引不是仓库，决策只住在自己的票里」 |
| 把 `retro` / `domain-modeling` 改写成中文或改例子 | **先搬原件，用两周再谈**——先改就回到「自己想改」的老路 |

## 五、还没解决的（等验证或等条件）

1. **一条都没验证。** 「撞墙九成是重复」是从当天三次个案推的，**样本只有 3 个**。要一两周的撞墙记录才能确认。
2. **「减少落点」的代价没人量过。** 读者要多跳一次；省下的是改的人的时间，花掉的是读的人的时间，不是同一批人。
3. **指针可能断裂。** `doc_lint` 查死链只查「文件在不在」，查不了「这一节还在不在」。
4. **「读者不同」没法机判。** 新判据下「用各司其职麻痹自己」依然可能复发，没有闸能拦。
5. **历史欠账没盘。** 现有 14 份工序文档里哪些是「为凑行数拆出去」的，一份都没核过。
6. **`agent-craft` 的加载「保证」不了。** 它剩下的内容不是「不做就出错」，是「做了更好」，所以不值得为它上闸。只能靠在对应的工序文档里提一句（而它是全局技能，四个库共用，不能拆散塞进本库工序文档）。
7. **`retro` / `domain-modeling` 还没搬。** 决定是「先搬原件，用两周再谈改造」。

## 七、怎么处置这份文件

- **它是一次性报告，不是真身。** 不进 `接棒必读` 的索引表（那份要解散了），靠 `grep "文档内耗" docs/` 找。
- **不设行数上限**，也不进 `doc_lint` 的常规检查范围。理由：它写完就定格，不会再长。
- **后续有新结论，另起一份**（比如 `讨论-文档内耗_20261201.md`），**不回头改这份**。理由：快照的价值在于它记的是当时的判断，改了就变成「永远最新、永远不可信」。
- **它记的判断如果后来被推翻，也不要改这里**——去新的那份写「上次那个判断错了，因为 X」。历史留在原地，才查得出认知是怎么变的。

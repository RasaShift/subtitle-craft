# 讨论 · 文档内耗（2026-11-09）

> **这是一次讨论的快照，写完即定格，不再更新。** 后续有新结论另起一份，不往这里加；这里的判断后来被推翻，也不回头改——去新的那份写「上次错了，因为 X」。历史留在原地，才查得出认知是怎么变的。
> 不进 `doc_lint` 的常规行数上限（按一次性报告处理，见末节）。读者预设：三个月后接手的人，只读这一份要能重建判断。

## 一、起因

用户的观察（确认过是**常态**，不是这两天的个别情况）：

> 有 1/3 的时间和精力，消耗在修改和缩减自己写的东西上面。

触发点是 2026-11-09 一天里连撞三次：

| 撞的 | 数字 | 真实原因 |
|---|---|---|
| `docs/接棒必读.md:42` | 单行 917 字符（上限 900） | 那行在复述判定记录已有的内容 |
| `docs/工序-审稿.md` | 137 行（上限 130） | 定档样例在 `examples/新剧接入.md` 也有 |
| `docs/协作协议.md` | 135 行顶格 | §4 旧广播该归档没归档 |

**三次没有一次是「内容真的多」。** 全是重复、该归档、放错位置。于是真问题变成：**这 1/3 是上限造成的，还是别的东西造成的？**

## 二、四轮讨论：每轮改变了什么判断

### 第一轮：以为上限太硬

用户提议「超 20% 才改、改回 70–80%」。我提了分级告警（超限 WARN、超 20% ERROR）加余额提示。

**这一轮方案后来被自己全否了。** 转折点是意识到：`doc_lint` 能看见的只有行数，所以所有优化动作都会被压成「凑行数」；而凑数字时，最先砍掉的往往不是废话，是判断依据。

### 第二轮：以为是上限，其实是落点太多

把当天的「改文档」拆成两类：**写新内容**（有价值）和**把同一件事同步到第 2 到第 10 个地方**（纯损耗）。后者占六成以上。

实例：「审稿降为可选」改了 10 处，真正需要独立写内容的只有 2 处（`工序-审稿.md`、判定记录），其余 8 处是「那里也提到了工序，所以得跟着改」。

**判断变成：内耗的根不是上限，是同一批事实有多个落点。**

### 第三轮：以为挪文件能减负

用户追问两句：各司其职是不是话术？挪文件不还是挪，总量没变？

**两句都成立。** 修正后的判断：

- 「各司其职」一半是话术。真需要分的只有手册 vs 判据（内容不重叠）；`README` / `接棒必读` / `流程总图` / `做法` **四份都在说「工序有哪几道」**，是同一事实说四遍。
- 挪文件确实不减少总量，它只改变「**每次干活必须读的量**」。正当理由只有一条：这份内容不会被每次读到，却占着每次都要读的位置。
- 指针的价值不是「减少阅读」，是「降低遗漏」。

当天一次具体的挪错：定档样例从 `工序-审稿.md` 挪到 `examples/新剧接入.md`。它属于「写定档的人当场要看」的第 1 级，挪走只因为塞不下——**分类错误被行数上限逼出来的搬家**。

### 第四轮：判据要换，不是阈值要调

读了外部技能包（见第四节），最关键的一条：

> Agents told to "streamline" optimise for **length**, because length is the thing they can see.

**所以真正的解法不是调阈值，是换判据**：从「多少行」换成「删掉这句，读的人行为变不变」（no-op test）。

## 三、定下来的十条

| # | 结论（正面动作） | 理由 |
|---|---|---|
| 1 | **上限值保持硬线**：130 行 / 900 字符 / 60 行 | 这些数代表「一页能读完」，放宽等于自欺 |
| 2 | **撞墙按三步诊断**：① 这段是不是在复述别处（是→删细节留名字）② 该归档的有没有归档（该→搬 `archive/`）③ 都不是，才谈压缩或拆卷 | 当天三次撞墙，两次栽在第①步、一次在第②步，没有一次到第③步 |
| 3 | **拆卷判据用「有没有另一批读者」** | 没有另一批读者、只是塞不下，正确动作是删内容或改写法，不是拆文件 |
| 4 | **同一批事实只在一处写内容，其余写名字** | 一件事改 10 处，真正需要独立写内容的只有 2 处 |
| 5 | **`buddy-workflow` 删除** | 41 行内容 100% 被 `MEMORY.md` 覆盖（输出偏好、多库分工），唯一独有的 Obsidian 双链一年用不到几次 |
| 6 | **`agent-craft` 改成按活加载**：改工具 / 写检查 / 做验收 / 拆技能前查，其余活不加载 | 199 行里 90% 是施工细节，只在上述几类活里用；核心六条早就在用户记忆里，每轮注入 |
| 7 | **`接棒必读` 解散**：导航进 `MEMORY.md`，「现在到哪了」进台账 | 它装了两样性质不同的东西：下个月仍成立的（导航）和一次性的（状态） |
| 8 | **判定记录换成 ADR 格式**：一段话 + 可选 `Status`（原来的「重开条件」映射到它，不自创） | 原文：「That's it. An ADR can be a single paragraph.」我们比它复杂，而复杂出来没人读 |
| 9 | **先搬外部原件，用两周再谈改造** | 先改就回到「自己想改」的老路；原件的判断力在我们之上 |
| 10 | **`GLOSSARY` 加 `_Avoid_` 字段**（「别叫什么」） | 我们只有「定义 + 在哪」，而「别叫什么」恰恰最有用——当天刚判过一词二义 |

## 四、外部参考：学到的八条

参考位置：`E:/Workedbuddy/电脑管家/.workbuddy/_research/skills`（下称「参考库」）。读的五份都在参考库下：.agents/writing-docs.md、docs/productivity/handoff.md、docs/productivity/writing-for-agents.md、skills/engineering/retro/SKILL.md、skills/engineering/domain-modeling/SKILL.md（含 ADR-FORMAT.md 与 GLOSSARY-FORMAT.md）。

**1. 三种病有名字了**（`writing-for-agents.md`）

> Pruning: single source of truth, relevance, and the no-op test applied sentence by sentence, against **duplication**, **sediment** and **sprawl**.

| 病名 | 我们的样貌 |
|---|---|
| duplication | 工序事实写在 README / 接棒必读 / 流程总图 / 做法四处 |
| sediment | `接棒必读:42` 那行，11-08 与 11-09 的结论一层层叠上去，从没清理 |
| sprawl | 一个工序拆成主干 / 判据 / 手册 / 实证四份 |

**2. 换判据：no-op test**

> delete the line and ask whether the agent's behaviour changed.

删掉这行，读的人行为变不变？不变就是废话。配套一句更狠：

> When a sentence fails, **delete the whole sentence rather than trim words from it**.

整句删，别改词——改词结构没变，下次照样撞。

**3. 两种负载**（context load / cognitive load）

- **Context load**：每轮常驻、不管用不用都付的钱（常驻文件的一行、技能 description）
- **Cognitive load**：记住「有哪些文档、什么时候用」的钱

「指过去不还得读」混淆了这两笔账。`接棒必读:42` 那 900 字符的错不在长，在**把「偶尔要用」的东西放进了「每轮付钱」那一层**。

（一条不适用：原文说「不要最小化 cognitive load，那是人类能动性的代价」——我们不成立，靠文件记不靠脑子记。）

**4. 挪文件的正确姿势：progressive disclosure**

> the ladder from in-file step, to in-file reference, to **disclosed reference behind a pointer**.

三级是固定位置：① 文件内步骤 ② 文件内引用 ③ 指针后面的按需披露。**判断该不该挪，看它属于哪一级，不看还剩几行。**

**5. 治「同步十处」的唯一办法：从不复制**（`handoff.md`）

> The document **references specs, plans, ADRs, issues, commits and diffs by path or URL, and never copies them**. That keeps the file small, and it keeps the settled detail **in one place instead of two copies that drift apart**.

**6. 什么该进常驻层：问「下个月还成立吗」**（`handoff.md`）

> Ask whether it's **true next month**.

成立 → 常驻层；一次性的活 → handoff / 台账 / 日志。`接棒必读:42` 那行里，「11-08 台账剩 2 条」下个月不成立，「判据要事前可判」成立——两种混在一行，谁也挑不出来。

**7. ADR 比我们简单得多**（`ADR-FORMAT.md`）

> That's it. An ADR can be a single paragraph.

写 ADR 的三条件（全成立才写）：① 难以逆转 ② 没有上下文会让人困惑「当时为什么这么干」③ 是真的权衡过。

**8. 术语表缺一个字段**（`GLOSSARY-FORMAT.md`）：`_Avoid_: Purchase, transaction`——「别叫什么」，我们完全没有。

**另外记一条没搬的**：`retro`（收工按七类扫环境改进点）和 `domain-modeling` 原件已决定搬，尚未搬。`wayfinder` 长在 issue tracker 上，我们没 tracker，只借它一条概念：「map 是索引不是仓库，决策只住在自己的票里」。

## 五、被否掉的方案（防止重提）

| 方案 | 为什么不做 |
|---|---|
| 超 20% 才改、改回 70–80% | 把「搬走一块」变成「必须砍够 30%」，凑数字时先砍掉的是判断依据 |
| 分级告警（超限 WARN / 超 20% ERROR） | 掩盖「撞墙 = 有重复」这个信号，而信号是唯一提醒 |
| 收工统一清 WARN | 攒着处理必然忘——`做法.md` 里的判据：「靠自觉的东西等于没有」 |
| 余额提示（剩 ≤5 行时列出） | 不是错，是缓办：它只让撞墙提前知道，不解决为什么撞 |
| 用 `wayfinder` 整套替换台账 | 它长在 tracker 上，我们没有；只借「map 是索引」一条概念 |
| 把 `retro` / `domain-modeling` 译成中文或改例子 | 先搬原件用两周，先改就回到「自己想改」的路 |

## 六、还没解决的

1. **一条都没验证。** 「撞墙九成是重复」是从三次个案推的，**样本 3 个**。要一两周的撞墙记录才能确认。
2. **「减少落点」的代价没人量过。** 读者要多跳一次；省的是改的人的时间，花的是读的人的时间，不是同一批人。
3. **指针可能断。** `doc_lint` 查死链只查文件在不在，查不了「这一节还在不在」。
4. **「读者不同」没法机判。** 「用各司其职麻痹自己」在判据下仍可能复发，没有闸能拦。
5. **历史欠账没盘。** 14 份工序文档里哪些是「为凑行数拆出去」的，一份没核过。
6. **`agent-craft` 的加载保证不了。** 它剩的内容不是「不做就出错」，是「做了更好」，不值得上闸。只能靠在对应工序文档里提一句（它是全局技能，四个库共用，不能拆散）。
7. **`retro` / `domain-modeling` 还没搬。**

## 八、怎么处置这份文件

- **一次性报告，不是真身。** 指针在 `docs/文档落点表.md`；不进接棒必读的索引（那份要解散了）。
- **不设行数上限**，不进 `doc_lint` 常规检查（文件名不在 `LIMITS` 里）。
- **后续新结论另起一份**（如 `讨论-文档内耗_20261201.md`），不回头改这份。
- **判断被推翻也不改这里**——去新的那份写「上次错了，因为 X」。

### 判据要事前可判：「事后 100%」不等于工具能算

- **结论**：规则清单 MF8 的第二条原写「同刻有署名行被删」，并注明「旧库 49 条 100% 满足该交集」。实测只有 **41/49（83.7%）**，容差放到 2 秒也不变——因为那是**事后**视角：人删署名行时顺手把底纹条一起删了。工具运行时看不到「将被删」，只能看当前文件。改成「同一起始时间还有别的非空 Dialogue 行」后 **49/49 成立、0 条孤单**，还顺带挡住了「正文里孤立方块行被误删」。
- **理由**：判据多半从人工校对报告里提炼，而报告写的是「人当时怎么做的」，不是「机器现在怎么判」——前者含未来信息（他接下来会删什么），后者只看当下状态。凡从报告搬一条判据，先问：**这条只依赖当前文件吗？** 不是就得改写成能算的形式，别把「事后吻合」当成「事前可判」。
- **重开条件**：出现「必须看上下文、单条文件判不了」的规则（比如要靠前后条才能判断的折行）时重估——那时该改的是工具接口（允许读相邻条），不是把判据缩水成能算的样子。

### 改动只认触发点、不认引用面：提交前扫四类字串

- **结论**：改了 A 处，B/C/D 还说着旧话——这类问题不靠记性防，靠提交前 `grep` 四类：① 旧计数（工具数 / 行数）② 刚废掉的规矩原话（如「两套并存」）③ 让你改的那句原文（确认它还在）④ `VERSION`。
- **理由**：剧库一天内报了四处同形（`GQ-20`）：协议 §5 与 §6.1 定了相反的编号规矩、§6.7 指挥它改一句 12:45 就改完的话、§8 预告扫一个它没有的目录、`doc_lint` 加 35 行而三个版本 `VERSION` 同号。四处都不是笔误，是「改动只处理了被点名那一处」。**与 `GQ-17` 不合并**：那条是跨文件副本漂移（判法是副本只留一份），这条是同一文件内部加代码元数据（判法是扫引用面）。
- **为什么第 4 类单列**：版本号不是文档，`grep` 文档扫不到；它一忘，下游只能把 30 个工具全 md5 一遍才能判新旧——把本该一次 grep 的活推给了每个使用方。
- **重开条件**：出现第五种关联面——既不是文本、也不在 git 里（环境变量、外部系统状态）。那时这条判法不够用。

### 检查器的「一致」必须双向：单向包含不算差集

- **结论**：两边各有状态的检查器，必须同时报 `A − B` 和 `B − A`。只查一个方向还输出「全部一致」的，比没有检查器更危险。
- **理由**：实测剧库那版 `recon.py`——它报「全部一致，不用读协议」，而当时 `GQ-20`/`GQ-21` 正挂在待报第一节、协议 §5 里根本没有。它只做了「§5 的号在待报里有没有交代」，新报的、§5 还没收的一律看不见。**这与 `GQ-12/13/18` 同病（检查说通过、实际没查），只是长在检查器自己身上。**
- **附带一条归属**：两边都要跑的检查器，**会写文件的拷副本，只读的直调原件**；真身放 `tools/`。只读件拷副本除了制造版本漂移没有好处（`text_scan` 一直直调，没出过事）。
- **重开条件**：改成双向后仍漏（如正文里提到的编号被当成条目），说明问题不在差集方向，在编号的存放位置。

### 技能不触发：规矩在记忆里也不够，要靠 description 触发词

- **结论**：技能能不能被拉起，只看 description 与首句的匹配。记忆里那句「开工先加载」是背景偏好，读到了也不等于会执行；要覆盖新场景，就得把场景词写进 description。已把「接棒 / 交接 / 接手 / 续上」补进 `agent-craft` 与 `buddy-workflow` 的触发词。
- **理由**：2026-11-09 实测两次——用户记忆每轮无条件注入，`agent-craft:103` 也明写「『开工先加载技能』这件事本身进用户记忆」，15:05 接棒那轮照样一次没读 `SKILL.md`。**记忆能被读到，但不会被当成「现在去执行」**；description 直接参与技能匹配，是唯一自动生效的入口。这也解释了过去几个月为什么"写了规矩还是不生效"：一直在补文案，没补入口。
- **连带修**：`#28`「技能不触发也没误事」只对 **4 份字幕技能**成立——它们只是索引页，判据正文在 `docs/工序-*.md`，短路了照样判对。这条被扩成「所有技能」之后就变成了免罪符，已在接棒必读收窄。
- **重开条件**：出现「description 已含场景词、仍不触发」的实例——那问题在技能的注册 / 发现机制，不在文案，改文案没用。
- **已验（2026-11-09 15:39）**：新会话首句只说「接棒」，第一步加载 `agent-craft`、第二步 `buddy-workflow`，之后才读接棒必读与台账——顺序也对。**改前改后同一天两轮，差别只在两头补没补：记忆改措辞解决「知道」，description 补词解决「被拉起」，缺一头都起不来。**

### 子 Agent 只收「结论 + 出处」，不单收结论

- **结论**：派子 Agent 解决的是**主上下文容量**，不是事实可信度，也不是省积分（它读的原文照样计费，还多一层总结开销）。三条同时成立才派：要读的比要交的多一个数量级 / 结果能独立验证 / 结论不直接进判据。回来**必抽查一条指针**。
- **理由**：只返回结论等于把证据和推理路径一起丢掉——主方没法复查，于是不再复查。结构上就是剧库 `recon.py` 那次：报「全部一致，不用读协议」，而两条新条目正挂在待报里。另外它不知道自己没查到时会补全，这类错最难看穿，因为主方拿的是二手货。
- **只能落 0 级**：子 Agent 是运行时行为，仓库里任何检查都拦不住；做成流程、模板或钩子，就落进 `docs/做法.md:31` 那档 ✗「要靠人读才算生效的东西等于没有」。所以落地只有一行判据进 `agent-craft` 第 2 步，不建模板文件。
